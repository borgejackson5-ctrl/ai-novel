# 灵阅平台 · 云服务器部署指南

> 目标：把项目搬到 Ubuntu 22.04 的 2核4G ECS，通过 `http://<公网IP>` 即可访问。
> **本机实测 `120.55.113.214:80` 不通**（域名可达性对照正常，是这台服务器的问题：未部署 /
> IP 已变 / 安全组没放行）。文档里的 `<公网IP>` 请按当前服务器的实际公网地址替换。
> 前置：Docker 已装，安全组已放行 22(SSH)/80(HTTP)（若跳板机是 Windows 才需要 3389）。
> 本文所有命令都在**服务器上**执行，SSH 登录后按顺序走即可。

---

## 第 0 步：确认安全组已放行 80 端口

阿里云控制台 → 实例 → 安全组 → 入方向规则，确保存在一条：
- 协议 `TCP`，端口范围 `80/80`，授权对象 `0.0.0.0/0`

> 没有这条，公网访问不到 nginx，后面全白搭。中间件端口（3307/6379/5672/15672/9201）**不要**放行。

---

## 第 1 步：配置 Docker 镜像加速（国内拉基础镜像的关键）

1. 打开阿里云控制台 → 容器镜像服务 ACR → 镜像工具 → **镜像加速器**，复制你的专属加速地址（形如 `https://xxxx.mirror.aliyuncs.com`）。
2. 用仓库里的模板 `deploy/daemon.json` 替换掉 `<你的加速器地址>`，写入 `/etc/docker/daemon.json`：

```bash
sudo mkdir -p /etc/docker
sudo cp deploy/daemon.json /etc/docker/daemon.json   # 先把地址改好
sudo systemctl daemon-reload
sudo systemctl restart docker
```

3. 验证：`docker info | grep -A3 "Registry Mirrors"` 能看到你的加速地址即成功。

## 第 2 步：把项目代码弄到服务器

二选一：
- **Git**（推荐）：服务器 `git clone <你的仓库地址>`（或 `scp` 整个 ai-novel 目录上去）。
- 确保这些文件在服务器项目根目录下都存在：`docker-compose.prod.yml`、`sql/init.sql`、`sql/seed_novels.sql.gz`、`backend/`、`frontend/`、`elasticsearch/`。

## 第 3 步：创建 .env（改掉所有弱口令）

在项目根目录（`docker-compose.prod.yml` 同级）。**推荐用仓库里的脚本一键生成**，它会自动
生成本机随机强口令，省去手改：

```bash
bash deploy/gen-env.sh     # 生成 .env，口令全部是 openssl rand 出的 32 位十六进制
```

脚本末尾会把 4 个关键口令打印出来（排查日志时要用），**抄下来，不要外传**。

> 脚本需要 `openssl`（Ubuntu 一般自带）。没有的话走手工路径：
> `cp .env.example .env && vim .env`，按下表改。

真正被生产 compose 读取的变量（`docker-compose.prod.yml` 里的 `${...}`）：

| 变量 | 说明 | 不填的后果 |
|------|------|-----------|
| `MYSQL_ROOT_PASSWORD` | 数据库口令 | 缺变量 → compose 直接报错退出，不会退回任何默认口令 |
| `REDIS_PASSWORD` | Redis 口令 | 缺变量 → compose 直接报错退出 |
| `RABBITMQ_USERNAME` / `RABBITMQ_PASSWORD` | 队列口令 | 缺变量 → compose 直接报错退出（RabbitMQ 内置 `guest` 只允许本机登录，容器网络内可用） |
| `PAY_NOTIFY_SECRET` | 支付回调验签密钥 | 空值 → 回调验签形同虚设 |
| `AI_API_KEY` | 接真 Key 才填 | 留空自动降级为示例内容，功能仍可演示 |
| `ES_DATA_DIR` | ES 索引落盘目录 | 默认 `./docker-data/elasticsearch`（在项目内） |

`.env.example` 里还有 `DRUID_USER/DRUID_PASSWORD`、`CORS_ALLOWED_ORIGINS` 两项，
但**生产 compose 并没有把它们传给后端**（prod profile 已关闭 Druid 监控台；同源反代下也用不到 CORS），
填了不生效，可以不管。

> 红线：`.env` 已被 gitignore，绝不提交；密钥只放服务器 `.env`，不进代码、不进聊天。

## 第 4 步：构建并启动（生产 compose）

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

- 首次构建会拉基础镜像 + `mvn` 打包 + `npm ci`，**约 5~15 分钟**（已配 Maven 阿里源 + npm 淘宝源加速）。
  ES 镜像构建时会从 `get.infini.cloud` 拉 IK 中文分词插件，**需要服务器能出外网**；拉不到会构建失败。
- 首次启动 MySQL 会按文件名顺序执行初始化目录里的两个文件：
  `01-init.sql`（建表 + 角色 / 分类）→ `02-seed-novels.sql.gz`（60 部作品 + 6500 章正文）。
  ES 首启约 60s。
- 后端启动时会检查 `t_user` 表：**为空且 `SEED_DEMO_ACCOUNTS=true` 时**才创建
  `admin` / `user`；**生产默认关闭**（那两个口令是公开写在 README 里的），
  需要演示账号就显式打开并同时用 `SEED_ADMIN_PASSWORD` / `SEED_USER_PASSWORD` 改掉初始口令。
  所以两个演示账号不需要 SQL，但**必须等后端起来**才存在。

查看进度 / 排错：

```bash
docker compose -f docker-compose.prod.yml ps          # 各服务状态
docker compose -f docker-compose.prod.yml logs -f backend    # 盯后端日志
docker compose -f docker-compose.prod.yml logs -f elasticsearch
```

### 4.1 给死信队列加上限（首次部署做一次）

7 个死信队列是「只留痕、不自动消费」的 —— 只进不出。没有上限时，一类持续失败
（模型侧长期不可用、ES 连不上）能把它们堆到打爆 broker 的内存/磁盘，而 broker 一旦进入
blocked 状态，**所有生产者都会被阻塞**，整个业务发不出消息。更麻烦的是没人会发现：
没人消费，也没有指标看深度。

上限加在 **broker 的 policy** 上，而不是队列参数上 —— RabbitMQ 不允许修改已存在队列的参数，
在代码里给 `QueueBuilder` 加 `x-max-length` 会让应用启动声明队列时撞 `PRECONDITION_FAILED` 直接起不来。
policy 不动队列、也不动队列里已有的消息：

```bash
bash scripts/apply-mq-policies.sh          # 幂等，可重复执行
```

生效后 `rabbitmqctl list_queues name messages policy` 里 7 个 `*.dlx.queue` 都会显示 `dlx-bounded`。
上限是 **10000 条 / 7 天**（`message-ttl` 单位是毫秒）。

> ⚠️ 策略只存在 broker 上，不跟代码走 —— **换服务器、清掉数据卷、重建 rabbitmq 容器之后都要再跑一次**。

## 已部署后更新代码（增量迁移）

> 适用于「服务器已经跑起来，后续改完代码再更新」的场景。**改代码无需从头再来**，只需三步：

**① 同步代码**

```bash
git pull          # 或用 scp / tar 上传新代码
```

**② 判断要不要执行 SQL 迁移（重要：已初始化的库不会重跑 init.sql）**

`init.sql` 只在 MySQL 数据卷**首次**初始化时执行。先分清两种情况：

- **库是当前版本新建的**（`init.sql` 已折叠了全部历史迁移、包含所有表和列）→ **不需要任何 migration**，直接跳到第 ③ 步。
- **库是更早版本部署的**，之后代码加了新表/新列 → 要手工补。`sql/migration_*.sql` 就是为这种老库准备的。

**⚠️ 迁移脚本不都是幂等的，别当成「随便重跑」**：

| 类型 | 脚本 | 能不能重复跑 |
|---|---|---|
| `CREATE TABLE IF NOT EXISTS` | add_admin_log / add_bookshelf_history / add_comment_table / add_feedback_table / add_novel_pending_edit / add_reader_tables / add_user_ai_config | 能（重复执行无副作用） |
| `ALTER TABLE ... ADD COLUMN` | add_chapter_audit / add_email_phone / add_novel_offline_time / add_reader_client_time / add_recharge_expire / add_chapter_no_unique | **不能**，第二次跑报 `Duplicate column name` / `Duplicate key name` |
| `UPDATE` | set_ai_quota_to_1 | 能（但会覆盖用户的额度值） |

执行时把密码交给**容器内部**去读，避免把明文写在命令行里：

```bash
docker exec -i ai-novel-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ai_drama' \
  < sql/migration_add_user_ai_config.sql
```

> `sql/init.sql` 是「单一 clean 版本」，会随功能迭代更新；`migration_*.sql` 是历史切片，
> 只增不改。两者的关系是：**新库看 init.sql，老库按需补 migration**。

**③ 重新构建并重启**

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

> 迁移脚本统一放 `sql/migration_*.sql`；以后每加一张表，就新增一个 migration 文件，
> 同时把同样的 DDL 折进 `init.sql`（保证新库一步到位）。

### 补充书籍数据（本地导入 / 修改公版书之后）

你在本地后台导入的公版书，只存在**本地** MySQL 里，不会自动同步到服务器 —— 线上看不到。
要让线上也有，走这三步：

**① 本地导出**

```bash
MYSQL_PASSWORD='本地数据库密码' bash scripts/export-seed.sh
```

生成 `sql/seed_novels.sql.gz`（书籍 + 章节正文，压缩存放）。脚本用 `REPLACE INTO`，
**重复执行不会数据翻倍**；`--complete-insert` 保证以后表加字段也不会列错位。

> 为什么压缩：几十本古典小说的正文接近 90MB 纯文本，直接提交会把仓库撑爆（而且每次
> 重新导出都会往 Git 历史里再堆一份）。gzip 后约 39MB。MySQL 官方镜像的初始化脚本
> 原生支持 `.sql.gz`，不需要额外处理。

**② 提交推送**

```bash
git add sql/seed_novels.sql.gz && git commit -m 'data: 补充公版书种子数据' && git push
```

**③ 服务器拉取并导入**

```bash
git pull
gunzip -c sql/seed_novels.sql.gz | docker exec -i ai-novel-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ai_drama'
```

> 密码交给容器内部去读（compose 已把 `MYSQL_ROOT_PASSWORD` 注进 MySQL 容器），
> 不用在服务器 shell 里 export，也不会出现在命令行历史里。

> 若数据库**从未初始化过**（全新部署），第 ③ 步可以跳过 —— `02-seed-novels.sql.gz`
> 会被容器在首次初始化时自动执行。只有**已经跑起来过**的库才需要手动导入，
> 因为初始化目录 `/docker-entrypoint-initdb.d/` 只在数据卷为空时生效一次。

**④ 重建搜索索引（必须，很容易漏）**

数据进 MySQL 了，但搜索走的是 Elasticsearch，**两套是分开的**。

`/novel/reindex` **需要管理员登录态**（无 token 直接 401），而后端容器没有对外映射端口，
所以要**经 nginx（80 端口）**调，并带上 token：

```bash
# 1) 取管理员 token
TOKEN=$(curl -s -X POST http://127.0.0.1/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"identifier":"admin","password":"admin123"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

# 2) 重建索引，返回 {"data": 60} 表示同步了 60 部作品
curl -X POST http://127.0.0.1/api/novel/reindex -H "Authorization: $TOKEN"
```

不重建的话，新书在书库里能看到、能读，但**搜不到**。

> 注意 `/novel/reindex` 是 **upsert，不清空索引**：如果删过作品，ES 里会留下
> 搜得到、点进去 404 的残影，要单独删（见下方排查）。

### 部署后排查：几个「看起来是 bug，其实是没做某一步」的现象

| 现象 | 真正原因 | 怎么修 |
|---|---|---|
| 书库能看到新书、点进去能读，**但搜索搜不到** | 数据进了 MySQL，没进 ES | 上面的 ④ 重建索引 |
| **搜得到、点进去 404** | ES 里有已删作品的残留文档（`reindex` 只 upsert 不清空） | `curl -X GET 'http://es:9200/novel/_search?size=200&_source=false'` 找出多余 id，再 `curl -X DELETE http://es:9200/novel/_doc/<id>` |
| 本地加了书，**线上没有** | 种子文件没提交，或提交了没导入 | 走「补充书籍数据」三步 |
| 改了 `init.sql`，**线上库毫无变化** | `docker-entrypoint-initdb.d` 只在数据卷为空时执行一次 | 手工执行，或删卷重来（**会丢数据**） |
| 后台导入同名书**报 500，但数据其实进去了** | 覆盖导入时旧章节被逻辑删除、残留行占用唯一索引 `uk_novel_no` | 已修（`ChapterMapper.deleteByNovelId` 物理删除）；老镜像需重新构建 |
| 打开页面**接口全 404** | 前端请求前缀是 `/api`，要靠 nginx 反代剥掉 | 确认走 80 端口访问，别直连后端 |
| 服务被 OOM kill | 2 核 4G，ES + 后端一起吃内存 | ES 已限 `-Xmx512m`、后端 `MaxRAMPercentage=75`；确认没在服务器上跑别的东西 |
| `admin/admin123` 登录失败 | 后端还没起来，或 `t_user` 表非空导致初始化跳过 | `docker logs ai-novel-backend` 找「初始化默认账号完成」 |

## 常用运维命令

```bash
# 全部重启
docker compose -f docker-compose.prod.yml restart

# 更新代码后重新构建 + 重启（后端/前端镜像变化时）
git pull && docker compose -f docker-compose.prod.yml up -d --build

# 看资源占用（2核4G 要留意内存）
docker stats

# 后端日志实时
docker logs -f ai-novel-backend

# 进 MySQL（密码从容器内部读，不在宿主机 shell 里 export）
docker exec -it ai-novel-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ai_drama'

# 查搜索索引状态（docs.count 应等于书库作品数）
docker exec ai-novel-es curl -s 'http://localhost:9200/_cat/indices?v'
```
