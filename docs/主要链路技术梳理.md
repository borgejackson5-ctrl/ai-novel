## 1. 登录 / 注册 / 鉴权链路

### 1.1 链路全景

```
前端表单
  └─> POST /auth/login 或 /auth/register
        ├─ [防爆破] 检查日志失败计数（Redis）
        ├─ [注册]   邮箱验证码校验 → 用户名/邮箱唯一 → BCrypt 加密 → 建号 + 绑角色
        ├─ [登录]   identifier 含 @ 走邮箱，否则走用户名
        │            ├─ 邮箱未注册 → 需验证码转注册
        │            └─ 用户名不存在 → 自动注册
        ├─ [校验]   BCrypt.checkpw 比对密码 → 状态检查（禁用则拒）
        ├─ [签发]   StpUtil.login(userId, model) → token
        └─ [返回]   { token, userId, nickname, avatar, role }
后续请求
  └─> Header: Authorization: <token>
        └─ SaInterceptor → StpUtil.checkLogin()
              ├─ 注解鉴权 @SaCheckRole / @SaCheckPermission
              └─ LoginUserUtil.getUserId() 取登录态
```

## 2. 支付 / 金币 / 订阅解锁链路

### 2.1 前置结论：**没有接真实支付渠道**

全仓库 grep `alipay` / `wechatpay` / `stripe` **零命中**，无任何第三方 SDK。
实现的是**自闭环收银台**：后端用 `mockPay` 模拟网关生成一份 HMAC 签名回调，再走**与真实回调完全相同**的 `handleNotify` 处理链路（`be/module/coin/service/CoinService.java:28-32` 类注释自述）。

这带来的好处是**回调侧的全部工程细节（验签/防重放/幂等）都是真的**，将来换成真网关只需替换 `mockPay` 那一段、保留 `handleNotify`。

### 2.2 链路全景

```
【充值】POST /coin/recharge
   ├─ 复用未支付老单（避免重复下单）→ 过期的置为已取消
   ├─ 雪花 ID 生成本地订单号，落 t_recharge_order（status=待支付）
   └─ sendAfterCommit → 延迟队列（TTL 15min + DLX）
          └─ 15 分钟后未支付 → OrderCloseConsumer → closeTimeoutOrder（仅 status=0 生效）

【支付】POST /coin/pay/notify（白名单，无登录态）
   ├─ 1. 验签：HMAC-SHA256，常量时间比较
   ├─ 2. 时间戳新鲜度：|now - ts| <= 5 分钟
   ├─ 3. nonce 一次性：Redis setIfAbsent 防同一回调重放
   ├─ 4. 金额二次校验：与库内订单金额比对，不符拒
   └─ 5. 幂等入账：markPaid（UPDATE ... WHERE status=0 原子 0→1）
             + userMapper.addCoin（原子加币）
             + 写 t_coin_log 流水   —— 同一事务

【消费】POST /subscribe/unlock
   ├─ Redisson 锁：lock:subscribe:{userId}:{novelId}:{chapterId|all}
   ├─ 双重检查：已购则直接返回
   ├─ 扣币（deductCoin 带 WHERE coin_balance >= amount 防超扣）+ 建订阅单（锁内小事务）
   └─ 阅读时 canRead 判定放行
```

|---|---|---|

### 2.4 检测结论

✅ **主流程完整**：下单 → 支付 → 入账 → 消费 → 鉴权闭环，且**回调侧的防重放与幂等覆盖较完整**。
⚠️ 两点如实说明：
- **无真实支付渠道**（模拟网关；回调处理按真实渠道实现：验签、时间戳窗口、nonce 防重放、幂等入账）
- **无退款 / 退币机制**（`t_coin_log` 注释预留了 `REFUND`，枚举未实现）
- `t_subscribe_order` 只有普通索引 `idx_user_novel`，**没有 `(user_id, novel_id, chapter_id)` 唯一索引** —— 并发防重完全依赖 Redisson 锁，少了一道数据库级兜底

## 3. 搜索链路

### 3.1 链路全景

```
【关键词搜索】GET /novel/search?keyword=&categoryId=&serialStatus=&minWords=&maxWords=
   └─ 分页钳位(size<=50, page<=10000/size)
        └─ NativeQuery.multi_match(title^3.0, intro^1.5, tags^1.0)
              + filter(status=1) + 筛选下推 + 高亮
                 ├─ 正常 → ES 返回
                 └─ 异常 → 【降级】MySQL LIKE（同样支持筛选）

【智能搜索】POST /novel/search/smart { query }
   └─ 意图解析（LLM / mock 规则）
        └─ 主查询：keywords + tags 作为 should(minimumShouldMatch=1)，分类只加 0.5 权重
              └─ 关键词全未命中 → 用分类兜底捞一批
                    └─ AI 不可用 → 降级为普通关键词搜索(degraded=true)

【索引同步】作品/章节变更
   └─ sendAfterCommit → search.novel.exchange → search.novel.sync.queue
        └─ 消费者只取 novelId 回查 DB → syncOne(id)
              ├─ 可见 → upsert；不可见 → 删除文档
              └─ 失败退避重投，5 次后进死信

【定时对账】每小时第 17 分
   └─ 比对 DB 应索引 id 集合 vs ES 实际 id 集合
        ├─ 少 → 补写；多 → 移除
        └─ 安全阀：DB 查出空结果 或 失效率>50% → 只告警不修
```
