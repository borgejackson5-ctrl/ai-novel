# 压测报告：AI 审核异步化（接口延迟）

> 目的：把「AI 审核改成异步」的收益量成可复现的数字，而不是一句没有依据的体感描述。
> 结论先说：异步化后接口延迟中位在 100ms 以内；同步等模型的那段耗时实测 0.5~0.8 秒。
> 另有一个早期记录过的 3 秒本次没有复现，可能来源见文末「已知局限」。

## 实验目的

把「AI 审核改成 RabbitMQ 异步」这件事的收益，从一句没有依据的描述，变成两个可复现的数字：

1. **接口延迟**：`POST /novel/publish` 返回要多久（异步化后接口只做「落库 + 投消息」）；
2. **审核链路耗时**：审核这件事本身跑了多久（= 改造前接口必须等的时间）。

## 为什么量的是延迟，不是吞吐

这里量的是**延迟**（一次提交要等多久），所以口径是**单请求耗时**，不是 QPS。
这份报告刻意不报吞吐 —— 要报吞吐得另做一套（并发梯度 + 资源监控），那是另一份报告的事。

## 测量方法

**脚本**：`scripts/async_audit_bench.py`（本次新增，可重复执行）

```bash
# 1) 起一份当前代码的实例（不要动 IDEA 里那个 8080）
cd backend && mvn clean package -DskipTests
java -jar target/ai-novel-backend.jar --server.port=8081 --app.ai-platform-daily-limit=5000

# 2) 跑（base 不带 /api —— 后端没有 context-path，/api 是前端 dev server 的代理前缀）
python scripts/async_audit_bench.py http://127.0.0.1:8081 8
```

**「接口延迟」怎么量**：脚本对 `POST /novel/publish` 计时（requests，取 `time.perf_counter()` 差值）。

**「审核本身耗时」怎么量**：不用日志，也不用改代码 ——
发布的瞬间会在 `t_mq_outbox` 落一条 `ai.novel.audit` 消息，审核完成时会把
`t_novel.audit_result` 写成 `AI 预审通过，等待人工终审`（或拒绝原因）。
脚本**每 200ms 轮询一次这个字段**，从「接口返回」到「字段被写上」的时间差，就是审核链路的耗时。

> 这个口径的好处：不依赖任何一个实例的日志 —— 项目同时跑着 IDEA 的 8080 和脚本用的 8081，
> 两个实例的消费者会争抢消息，谁处理都行，DB 是同一个。

**一个反证（说明这条链路真的在调模型）**：55 篇测试作品里有 **3 篇被 AI 审核判为「拒绝」**并写回了原因
（`audit_status=2`）。如果这条链路只是空跑，不会出现这个结果 —— 也顺带说明「拒绝」分支是活的。

## 实验结果

**环境**：本机（Windows）单实例，MySQL / Redis / RabbitMQ / ES 均为 Docker 容器，
模型 `deepseek-chat`（平台 Key，`t_ai_config`）。三轮独立执行，每轮 8 次串行 + 10 并发。

### 串行提交（每次发一部新作品，1 章）

| 轮次 | 接口延迟 min / p50 / max | 审核耗时 min / p50 / max |
| --- | --- | --- |
| 第 1 轮 | 61 / **112** / 361 ms | 0.2 / **0.8** / 1.1 s |
| 第 2 轮 | 49 / **74** / 182 ms | 0.2 / **0.5** / 0.9 s |
| 第 3 轮 | 46 / **63** / 98 ms | 0.2 / **0.5** / 0.8 s |

- **第一轮的 361ms 是冷启动样本**（JIT + 连接池 + DispatcherServlet 初始化），后续稳定在 100ms 以内；
- 三轮的接口延迟 p50 落在 **63~112 ms**，最小值 46~61 ms。

### 长简介（约 900 字，贴近真实投稿）

| 接口延迟 p50 | 审核耗时 p50 / max |
| --- | --- |
| 56 ms | **0.7** / 0.8 s |

> 作品预审送进模型的是「书名 + 简介」，简介上限 1000 字（`@Size(max = 1000, message = "简介过长")`）。
> 从短简介的 0.5s 到 900 字的 0.7s，**审核耗时随文本长度上升，但幅度不大**。

### 10 并发同时提交

| 指标 | 值 |
| --- | --- |
| 全部请求墙钟耗时 | **224~441 ms**（10 个请求） |
| 成功 | **10 / 10** |
| 单请求延迟 min / p50 / max | 122~157 / 163~327 / 208~427 ms |
| 这 10 篇的审核 p50 / max | 0.2~0.3 / 0.4~1.5 s |

10 个请求同时到达时，接口延迟只从 p50 63ms 涨到 163ms —— **因为接口不等审核**，
瓶颈不在模型上。这正是异步化要换来东西：`/novel/publish` 不再被 LLM 的耗时绑住。

## 结论

| 指标 | 实测 |
| --- | --- |
| 接口延迟（异步化后） | min 46ms、p50 63~112ms、并发下 p50 163~327ms |
| 同步等模型的那段耗时 | 审核本身 p50 0.5~0.8s（900 字简介 0.7s） |

异步化省掉的就是「同步等模型」那段时间，接口侧只剩落库与投消息。

### 一个早期记录的 3 秒为什么没复现

1. **可能不是这条链路**：作品预审只送「书名 + 简介」；章节级审核要把整章正文（几千字）送进模型，
   耗时会长得多。若「提交审核」指的是章节提交，3 秒是可能的，本次没有量那条链路；
2. **内容更长或模型更慢**：这次用的 900 字简介已在长度上限附近，仍只有 0.7s；
3. **可能是并发下的等待**：同步实现下多个请求串在同一个 Tomcat 线程池与模型连接上，
   排队会把耗时放大到秒级。这次 10 并发没有放大，是因为已经异步了。

### 引用这组数字时的口径

- 量的是**延迟**，不是吞吐；样本量 8~10 次，报的是量级而不是性能上限。
- 用「中位 60ms 左右」这种表述，不要写死某个值：p50 落在 63~112ms，并发下会到 163~327ms。
- 3 秒在本机没有复现，引用时要交代环境与文本长度，或改用定性描述：
  「接口只做落库与投递，不等模型返回」。

## 已知局限

1. **样本量小**：每组 8~10 次，不是 JMeter 级压测。报的是「延迟量级」，不是「性能上限」；
2. **同机**：压测脚本、后端、中间件都在同一台机器上，没有真实网络开销；
3. **审核耗时的口径**：从「接口返回」到「DB 里看到结果」，包含消息投递 + 消费 + 敏感词 + 模型调用 + 落库，
   比纯模型耗时略大（投递本身在毫秒级，见 `t_mq_outbox` 的 `create_time`/`sent_time` 同秒）；
4. **只量了作品预审**：章节级审核（`auditChapter`，正文进模型）没量，它是「3s」最可能的来源；
5. **轮询精度**：200ms 轮询，所以 0.2s 这个下限基本等于「一次轮询就看到了」。
