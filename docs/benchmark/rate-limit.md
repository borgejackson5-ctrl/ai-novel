# 压测报告：Lua 限流（固定窗口）

## 实验目的

验证 Lua 原子限流脚本对榜单接口的保护效果。

## 实验设计

- **接口**：`GET /rank/hot`
- **限流规则**：每用户每分钟 60 次（key=`novel:rate:{uid}`，窗口 60s）
- **压测**：JMeter 100 线程（共用同一 token）持续 10s 循环打榜单接口（单机瞬时约 130~140 QPS，10 秒共 1200~1400 个请求，远超 60 次阈值）
- **对照组**：开启限流 / 关闭限流（临时注释 `tryAcquire` 调用后重建 backend）
- **每轮跑前**：`DEL novel:rate:{uid}` 清掉上一轮未过期的计数 key

## 实验结果（2026-09-07，Docker 全栈本地环境，4 轮）

| 指标 | 开启限流（4 轮） | 关闭限流（对照） |
|------|----------------|----------------|
| 总请求数 | 1311 / 1414 / 1375 / 1261 | 745 |
| 200 响应数 | **60 / 60 / 60 / 60**（恒等于阈值） | 745（全量放行） |
| 400 + code 10004 数 | 1251 / 1354 / 1315 / 1201 | 0 |
| 拦截率 | 95.4% / 95.8% / 95.6% / 95.2% | 0 % |
| 后端 CPU 峰值 | ~110%（单核瞬时，含 JMeter 同机干扰） | **~157%**（高于开启组） |

注：对照组请求数（745）比开启组（~1300）还少——关闭限流后每个请求都要完整走「L1 miss → 查 Redis ZSet → 查 DB 重建列表」链路（L1 被高频打穿后 30s 内过期重建），响应变慢导致同窗口内完成的请求数反而更少，且 CPU 明显更高。开启限流时 95% 的请求被 Lua 在 Redis 侧快速拒绝，后端吞吐反而更高。

## 预期结论（已验证）

- 开启限流时，单用户 60 次后的请求全部被 Lua 脚本在 Redis 侧原子拒绝（HTTP 400 + 业务码 10004 RATE_LIMIT），**放行数 4 轮全部精确等于阈值 60**，无一次多放
- 限流 key 的 TTL 正常倒计时（窗口结束自动过期恢复访问）

## 实现要点

1. **为什么用 Lua 而不是 `INCR + EXPIRE` 两条命令**：两条命令非原子，并发下 `INCR` 后若 `EXPIRE` 未执行，key 永不过期，用户被永久封禁。Lua 脚本在 Redis 单线程内原子执行。
2. **固定窗口的缺陷**：窗口边界（如 59s→60s 切换瞬间）可能放过 2× 流量。若要更平滑，可换滑动窗口或令牌桶（Redis-Cell 模块）。本项目选固定窗口，实现简单、计数开销恒定。
3. **为什么不放在网关层**：本项目无网关，限流在应用层用 Redis 实现；有网关时应在网关层（如 Sentinel / APISIX）做。
4. **实测佐证**：100 并发线程打同一用户 key，4 轮放行数全部恰好 60。说明「读计数 - 判断 - 自增」三步在并发下没有竞态窗口，这正是 Lua 原子性的价值（若用普通 GET+INCR，并发首波可能同时读到 59 而多放行）。
