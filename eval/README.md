# 章节审查评测

清单 2.6 的验收标准是「能拿出一组标注样本 + 准确率/误报率，而不是'感觉好多了'」。
这个目录就是那把尺子：同一批样本、同一个打分脚本，改提示词前后各跑一次，比指标。

## 怎么跑

**一条命令**（推荐）：

```bash
python eval/run_all.py --label after-fix
```

它按固定顺序做五件事，任一步失败就停：① 四个中间件不在跑就起来（ES 等到应答）；
② jar 不存在、**或比任一 .java 旧**就重新打包（防"测的是旧代码"——那会让报告写着
「改完更准了」而其实没编）；③ 在 8081 起评测实例（带 `--app.ai-platform-daily-limit=500`），
日志落到 `D:\WorkBuddySave\ai-novel\logs\`；④ 样本作品不存在就先 setup；
⑤ 逐样本集跑 `review_eval.py run`，最后打印汇总表。

常用开关：`--cases review-cases,holdout`（默认这两个）、`--mode single|task|both`、
`--reset-quota`（跑前清零评测账号当日字数）、`--vs <旧label>`（跑完再比一次）、
`--keep`（别停实例）、`--skip-run`（只起环境、打印将执行的命令）。

手动方式（拆开排查时用，run_all 内部就是调这些）：

```bash
# 1. 起一个评测实例（把平台日调用上限放宽，否则一轮就把 100 次用光）
java -jar backend/target/ai-novel-backend.jar --server.port=8081 --app.ai-platform-daily-limit=500

# 2. 建评测作品并导入样本章（只需一次）
python eval/review_eval.py setup

# 3. 跑一轮（额度不够时脚本会直接拒绝，而不是跑一半）
python eval/review_eval.py run --label baseline --log <实例日志>
python eval/review_eval.py run --label after --cases holdout --mode single

# 4. 清理（只打印要删的 id，不自动删）
python eval/review_eval.py teardown
```

> ⚠️ **手工起实例时记得带上 `--app.rate-limit.enabled=false`**（`run_all.py` 已经默认带上）。
> 评测脚本是受控的压测客户端：一章接一章地背靠背调用，接口限流会把它当洪水打，
> 表现为后半本整片 429「操作过于频繁」、报告变成 `complete=false`。
> 而它**看上去只像「模型变差了」** —— 2026-09-22 实测过一次：holdout 的 h11/h12 直接失败，
> 章内召回从 0.88 掉到 0.73，纯属假跌。真实用户不会这么打。

### 额度：这一轮最大的坑（2026-09-18 被它打断过一次）

- **单章审查不扣个人额度**：它跑在 HTTP 线程里、有登录态，管理员走平台 Key，只占平台调用次数。
- **全文审查要扣**：它跑在 MQ 消费线程里，**没有登录态**，`isAdmin()` 是 false ——
  于是管理员也被当普通用户，按 `ai:user:usage:{userId}:{日期}` 扣当日免费字数（默认 3 万）。
  一轮 `mode=both` 大约 2500 字，连着跑十几轮就到顶。
- **打满之后的表现极具误导性**：不报错，而是「从某一章开始调用失败 / 任务被中止」，
  看起来就像「模型这一轮检出变少了」。所以脚本现在①开跑前量剩余，不够就**拒绝跑**
  （`--allow-low-quota` 可强行跑，但本轮标成不完整）；②跑完判完整性（单章有无失败、
  任务是否「已完成」、有没有审完所有章），不完整就在报告头部打警告，JSON 记 `complete=false`。

产物：`reports/<label>.md`（给人看的）与 `reports/<label>.json`（给下一次做差值的）。
`reports/.cases-map-<样本集>.json` 记录评测作品的 novelId 与每章 id —— 有了它，重复跑不会重复建数据。
**这个文件不入库**（在 `.gitignore` 里）：装的是本地那个库的雪花 id，换台机器就失效；
`setup` 会当场重建，而且**扩样本集时只补缺的章**，不重建作品。

**哪些报告入库**：只保留当前基线与被 `REPORT.md` / 本文档直接引用的轮次，历史轮次的原始产物
留在本地（不入库）。一轮 `mode=both` 会产生 3 个文件，十几次调参就是上百个 —— 结论在 `REPORT.md`，
过程产物没有必要都进仓库。

| c2 灯 | 5 | 错别字 ×2、语病、标点（书名号不配对）、**章内人名两种写法** |
| c3 更声 | 4 | 错别字、语病、标点（引号不配对）、**章内数字自相矛盾** |
| c4 灯市 | 4 | 错别字 ×2、语病、标点（英文句点） |
| c5 迟到的信 | 3 | 错别字、语病、标点（句号当省略号） |
| c6 尺 | **0** | 章内干净（误报基准）；但**跨章**有 2 处矛盾：人名写成「沈青悟」、刀写成「两尺长」 |

单章审查**结构上不可能**发现它 —— 这正好用来测「全文审查到底有没有跨章能力」。

### 留出集：`cases/holdout.json`（12 章 / 33 处章内 / 5 处跨章）

2026-09-19 从 2 章扩到 12 章。**原来 2 章时任何百分比都只能叫「方向性证据」**，
说出去站不住；扩到两位数以后，报告里的召回率与精确率才有解释力。

结构与 dev 同构，换的是皮：人名「柳砚秋」（dev 是「沈青梧」）、道具换成伞（dev 是刀）、
标点错以半角问号/半角逗号/省略号误写为主、不一致换成颜色与数字，另外多了两类
dev 里没有的（时间点、姓氏）。h2/h6/h12 三章**章内干净**，是误报基准。

**每处缺陷都有依据，不凭手感**（不确切的就不写进去）：

| 依据 | 用在哪 |
|---|---|
| GB/T 15834-2011《标点符号用法》4.11：省略号形式统一为六连点 | 「想了很久...」应为「……」 |
| 同上 5.1.3：引号/书名号两部分成对标在两端 | 只写前一半的引号、书名号 |
| 同上 4.5：顿号用于并列词语之间 | 「笔，墨，纸，砚」应为顿号 |
| 同上 附录 A.2（规范性附录）：问号以疑问语气为据，不看有没有疑问词 | 「他不知道自己该不该说出口？」 |
| 《第一批异形词整理表》GF 1001-2001 推荐词形 | 灯芯—灯心、成分—成份、弘扬—宏扬、纪念—记念、就座—就坐、糊涂—胡涂、含糊—含胡、凋谢—雕谢、含蓄—涵蓄 |
| 成语辨形 | 迫不及待（及 ≠ 急）、不禁（禁 ≠ 竟） |
| 教科书病句类型 | 缺主语、句式杂糅、搭配不当、重复赘余、定语语序不当、关联词误用 |

语病只取这几类硬伤，**避开「文风好不好」这种有争议的判断** —— 否则误报没法算。

### 射程外的样本：`cases/far-cases-v2.json`（24 章 / 9 处跨章 / 章内一律干净）

2026-09-19 新建（第九轮留的话：「要量 RAG 的账，得把 far-cases 扩到几十条」）。
上面那 12 章里每处跨章事实都落在「邻近检索 ±10 章」的射程内，**量不出语义检索的账**；
这一套专门把射程拉出去：

| 绕开谁 | 怎么绕 |
|---|---|
| 邻近检索（只看当前章 ±10 章） | 对照两章**距离一律 12 章**（f1↔f13 …… f12↔f24） |
| 名词表（按名字精确匹配） | 后面那一律**换称呼**：刀→那件兵器、石榴→那株树、黑麻绳→红绸、城南→城北 |
| 设定数字表（名词=数值） | 矛盾点不用「名词紧邻数值」这个形态，也不是专名写错一字 |

⇒ 这类矛盾要被检出，**只能是语义检索把前文找出来、再摆给模型**。

另有 3 处**「换了说法但事实一致」**（f21 / f23 / f24）是误报陷阱 —— 把「换了个说法」
当成「前后矛盾」报出来就记成误报。**整本章内无缺陷**，所以报出来的任何非跨章条目都是误报。

标注里可以显式写 `priorMark`（「前文那一半」的依据串），给 `retrieval_eval.py` 用；
不写它才退回启发式（挑不在本章正文里的特征串）—— 见下面「检索侧评测」那节。

## 打分口径

- **匹配认位置不认字**：报告片段在正文中的任意一次出现与标注区间有重叠即算命中。
  模型把「沈青悟」报成「沈青梧」是同一处，算命中；修法方向对不对单独统计（`fix_ok`）。
- **归一化与服务端同口径**：比对前去掉所有空白（服务端的反幻觉核对也是这么做的），
  否则会出现「服务端认为合法、打分脚本认为对不上」的假差异。
- **认四类**：错别字 / 语病 / 标点 / 前后不一致（与服务端 `normalizeType` 的收敛口径一致）。
- **人工复核**：机器只能判「落没落在标注区间上」。落不上的报告里，
  可能是「真问题、方向反了」或「推断错了的误报」—— 这两种性质完全不同，
  所以复核结论写在 `reports/<label>.verdicts.json`（键是 `章id|报告片段`），
  报告里会把「机器精确率」和「人工复核后精确率」分开列。**没复核就标「还没复核」，不假装知道。**
- **跨章标注单独算**：同一处跨章问题被重复报多次时只算 1 次检出，其余计「重复报告」。
  重复不是误报，但确实是噪声。

## 已知局限（读指标时必须一起读）

1. **召回率是乐观值**。缺陷是植入的，比自然文本里的更典型；章也短（150~260 字），
   缺陷密度远高于真实章节（真实章节 2000+ 字）。所以**绝对值不能当线上水平**，
   它能说明的是「同一把尺子下，改动前后差多少」。
2. **一次跑有随机性，而且比之前估的大**。模型温度不是 0。第九轮在 12 章留出集上
   把同一配置跑了两轮：**章内召回 82% vs 88%**；把 RAG 开关两组四轮放一起看，
   范围 **76%~88%（12 个百分点 = 33 处里差 2~4 处）**。
   ⇒ **单轮差值小于 ~3 处（约 9 个百分点）就别当结论**；要下结论至少两轮，看范围不看单点。
   抖动集中在「前后不一致」这一类（2~6），错别字/标点/语病三类只抖 ±1；
   跨章命中（四轮都是 3/5）与干净章误报数（四轮都是 0 条）是稳定信号。
3. **改动是打包的**。`after2` 同时含「工具权限修复 + 提示词收紧」，
   没做「只修 bug 不改提示词」的隔离组 —— 归因靠的是模型自己写在 summary 里的原话
   （「本次工具调用均返回未登录或登录已失效」），而不是靠控制变量。要严谨就得再跑一组。
   （第九轮另做了一组隔离：RAG 注入开/关各两轮。结论是**在 12 章这个尺子上量不出差异**，
   因为跨章事实都落在「邻近检索 ±10 章」的射程内。见 REPORT 第九轮。）
4. **跨章的「时间点」和「称谓」这两类，测出来是做不到的（第十轮）。**
   六轮基线（注入 3 条／关注入，各两轮以上）跨章命中恒定 3/5，缺的始终是这两类。
   三种办法都试过、都没用：把这两类写进提示词的动作清单（跨章仍 3/5）；把前文注入条数
   从 3 放到 8（跨章 3~4/5，**而且干净章开始报误报**，误报基准破了）；服务端也做不出判据
   （时间表达是开放集合，姓氏要判「是不是同一个人」）。**目前按已知能力边界处理**：
   要么接受它，要么走 REPORT 第十轮末尾那条「服务端先把该比的两句配好对」。
   ⚠️ 这一轮踩到的坑同样要记住：**提示词里出现留出集的原文 = 数据泄漏**，
   它会让假提升看起来跟真提升一模一样（那次跨章 4/5 就是这么来的）。
5. **只测审查，不测创作**。续写/润色没有 ground truth，只能人读；
   这套东西只覆盖「有确定对错」的审查链路。

## 跨章一致性：从「靠模型自觉」到「机制保证」

`after2` 之后，跨章一致性靠的是「提示词要求模型必须用工具去查前文」——
**仍然是「模型愿不愿意照做」的问题**。所以加了机制，一共两层：

### 第一层：写法（`t_novel_glossary`）

1. **攒表**：审查时模型顺带返回本章的专有名词（结构化输出的 `names` 字段），
   服务端校验「必须在本章正文里原样出现」后写进表（记首次出现的章号）。
2. **注入**：审下一章时把「本书已确立的写法（第 N 章）」放进提示词，模型照着对一遍。
3. **服务端比对**（不看模型脸色）：本章出现「与表里某个名字同长度、同位置只差一个字」的写法，
   直接产出一条「前后不一致」，与模型报的走同一套去重键合并。

**实测教训一（2 字）**：第一版把 2 字名字也纳入比对，结果一章写灯笼的正文里
「灯下 / 灯还 / 灯芯 / 灯笼 / 灯纸」全被判成「与第 4 章的『灯市』不一致」——
一轮下来十几条全是误报（报告数 18 → 38、精确率掉到 74%）。收到 **3~4 字**之后才干净。

**实测教训二（虚词）**：为了修「一章里写对五处、写错一处会漏报」，
去掉了「本章出现过标准写法就整条跳过」的短路 —— 结果表里的「旧地图」开始跟正文里的
「搁**在地图**边上」「**把地图**卷起来」撞上，又是两条误报。补的判据是
**差异位置上不能是虚词**（的地得了着过在把…）：真实的写法错误差异字都是实词（青/清、芯/心、萧/肖）。

**实测教训三（谁也别断言）**：表里可能同时有「灯芯（第 3 章）」和「灯心（第 6 章）」
（模型把自己写错的名字也报过）。这时**不能拿其中一条当标准**，所以只差一字的条目归成一**族**：
注入时摆在一起（「本书两种写法都用过」），报告按证据分档给语气 ——
那个写法在**多个被审过的章**里都出现过才说「此处应一致」，否则只说「请确认统一为哪一种」。
顺带修了一个漏报：以前两种写法都进表后会被「表里已有这个写法」全挡掉，**书里两种写法并存却永远不报**。

### 第二层：设定数字（`t_novel_fact`）

写法的表只管名字。数字（刀是两尺还是三尺）以前完全靠模型读前文，而表上线后模型更不读前文了
（工具调用 16/12 → 0/0）。所以数字也攒表：

1. **攒表**：模型顺带返回 `facts`（形如 `"伞骨=七根"`），服务端过三道校验才入库：
   名词在正文里、数值在正文里、**两者相距不超过 10 字** ——
   不校验距离的话，「他今年二十八岁，柳砚秋站在门外」会被读成「柳砚秋=二十八」。
2. **比对**：同一个东西本章写的数与表里不同就报一条，**中性表述**（「请确认以哪个为准」）。
3. **先归一化再比**：`NumberWords` 把「七根」与「7 根」都还原成 7 —— 直接比字符串就是一条误报。

### 已知边界（决定了什么时候不能信它）

- **表是空的时候没有基准**：第一次审某一章时它无从比对。全文审查是并发消费，
  所以「第一次跑一本新书」时先被处理的章拿不到后处理章的名字，第二轮才稳定。
- **数字的覆盖度取决于模型报不报**：服务端比得准，但前提是表里有那条数字。
  实测 8 章只攒到 2~3 条，dev 那处「刀 三尺 / 两尺」就是因为模型从没报过而漏掉的。
- **表里可能混进错写**，后果是同一个错写**只会被报一次**（少提醒，不是报错）；
  反方向的误报已由「族 + 分档语气」压掉。
- **2 字名字**只有提示词那一条路（模型照表核对），服务端不判。

## 混合检索评测（向量 + 关键词）

生产检索是**混合**的：向量那一路按语义找、关键词那一路（IK 倒排）按字面找，RRF 融合。


- **判定**：返回的块文本里含不含依据句（去空白后比对）。依据句在原文里唯一出现，

- `Top3 有用` 是这条评测线上的口径；**审查那边实际注入几条由 `app.rag.max-context-chunks`
  决定，第十一轮从 3 提到了 5** —— 报指标要跟那个数对齐（看 Top3 还是 Top5 不一样，
  见下面那节量出来的结论）。

### 另一个入口：只看「依据有没有被检索到」（`retrieval_eval.py`）

`review_eval.py` 报的「跨章命中」是**三段相乘**：检索找到 → 摆进提示词 → 模型去比。
哪一段掉了，从总数上看不出来（两个方向都撞到过：注入进去模型也不报；两路都找到了、
融合却把依据挤出去）。所以另有一个只看第一段的工具：

```bash
python eval/retrieval_eval.py --cases far-cases-v2          # top_k 默认 3，与服务端默认对齐
python eval/retrieval_eval.py --cases holdout --top-k 5
python eval/retrieval_eval.py --cases far-cases-v2 --chapter f19    # 只看某一章
```

- **判据**：检索回来的**前文**块里，有没有哪一块含「前文那一半」的依据串 ——
  也就是「模型要核对时，手里有没有那份依据」。标注里可以显式写 `priorMark` 指定那一半；
  不写就退回启发式（挑不在本章正文里的特征串）。**要写 `priorMark`**：
  `matchAny` 是给打分匹配用的，它常只写本章那一边，启发式就会整条跳过（实测漏掉 3/5 条）。
- **实现方式**：直连 ES + 向量模型，**复刻**服务端那三段（两路 + RRF 融合），
  好处是不用起实例、可以逐条调 `--top-k` 扫。⚠️ 代价是**参数抄了一份**：
  改 `ChapterVectorServiceImpl` / `HybridRanker` 里的 RRF_K、候选倍数、上限，要同步改这边。
  （复刻准不准用真实案例核过：h10 那条在接口与复刻里都是「融合后掉出 top-3」。）
- **它量出来的第一个结论**（第十一轮）：两路各自都能把依据排进 top-5，但**只取前 3 条时
  融合会各丢一条** —— 依据块排在 4~5 名，被「两路都排中游」的块压下去。
  三个样本集合计 16 处对照：top-3 时融合 14/16，top-5 时 16/16。
