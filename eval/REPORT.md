# 章节审查评测报告（清单 2.6）

时间：2026-09-18　样本：dev 6 章 / 留出集 2 章　账号：`admin`　模型：平台 Key（deepseek-chat）

## 结论

1. **章内四类问题本来就不差**：错别字 / 语病 / 标点 / 前后不一致，改动前召回 85%（dev）、80%（留出集），
   类型判对 17/17，反幻觉丢弃 0 条。**这部分没有大问题，不需要大改。**
2. **跨章一致性原本是「坏」的，不是「不够准」**：全文审查里每一次工具调用都抛「无权限操作该作品」，
   模型于是给出一份没核对过前文的报告 —— 甚至写下「已通过 searchWordNearby 核对，写法一致，未发现前后矛盾」。
   修完两个真 bug 后，**全文审查的跨章检出从 0/2 变成 2/2，dev 与留出集都是**，这个变化在噪声带之外。
3. **跨章一致性最后还是做成了机制，而不是靠提示词**：加了一张作品级名词表，
   由服务端直接判定「本章写法与书里已确立的写法只差一个字」。改法见下面「第二轮」那一节。
4. **章内召回的提升（85%→90~95%）在噪声边缘，不能单独下结论**：同一份代码跑两次本来就差 ±5 个百分点。
   能站得住的是：**没有一项回退，精确率也没变差**。
5. **代价要说清**：单章耗时 1.5s → 2.3s，全文 12s → 15s；多了一次建表迁移；
   多出来的时间花在工具往返与服务端比对上的，是「跨章不靠运气」的价钱。

## 怎么测的

```bash
java -jar backend/target/ai-novel-backend.jar --server.port=8081 --app.ai-platform-daily-limit=500
python eval/review_eval.py setup && python eval/review_eval.py run --label baseline
```

- **样本**：`cases/review-cases.json`（dev，6 章 20 处章内 + 2 处跨章）、
  `cases/holdout.json`（留出集，2 章 5 处 + 2 处跨章，人名与错误类型都换过）。
  植入式缺陷，每条标注给出 `wrong`（在正文里唯一出现，用来定位）。
- **打分**：报告片段与标注区间**有重叠即命中**（认位置不认字）；比对前去掉空白，与服务端反幻觉核对同口径。
- **人工复核**：机器判不了的落空报告，由人过一遍，结论写进 `reports/<label>.verdicts.json`。
  报告里「机器精确率」和「人工复核后精确率」分开列。
- **噪声带**：`baseline` 与 `baseline2` 是同一份代码的两轮，用来标出随机波动（见下表）。

## 发现的问题

### ① 全文审查的跨章核对从来没生效过（真 bug，最严重）

审查工具复用了一个带归属校验的方法（`pageAuthorVOByNovel` → `requireOwnerNovel`），
而全文审查跑在 MQ 消费线程里，**那里没有登录上下文** —— 于是每一次工具调用都抛「无权限操作该作品」。
工具异常被框架转成一句错误提示交给模型，模型照常给结论。

两条实测证据（模型自己写在 summary 里）：

> 本次工具调用均返回「未登录或登录已失效」，无法核对前文，故前后不一致一项仅报本章内部可确认的矛盾。

> 专有名词「柳砚邱」及道具「七根伞骨的伞」已通过 searchWordNearby 核对，写法与前后章一致，未发现前后矛盾。

第二句是**假的保证**：工具明明返回了错误，报告却说核对过。这比漏报更糟 ——
作者会以为自己已经查过了。上面那条核心指标「全文·跨章召回 0/2」，根因就在这里。

### ② 100 章以后的书，工具一个章都找不到（真 bug）

`ChapterReviewTools` 里页大小写的是 300，而服务端会把页大小钳到 `PageParam.MAX_PAGE_SIZE`（100）。
「本页不满 ⇒ 后面没有更多章节」这个判断还拿 300 去比 —— 条件永远成立，
于是每本书都只有第一页，第 100 章往后一律回一句「本书没有第 N 章」。不报错，只是查不到。

### ③ 「要不要查前文」全凭运气（稳定性）

同一份代码、同一章：单章审查那轮模型主动查了 5 次前文、检出了跨章人名矛盾；
全文审查那轮一次都没查、直接漏掉。跨章检出率在 **0/2 ~ 2/2** 之间跳。

### ④ 报矛盾时方向报反（正确性问题）

实测里 6 次出现同一个毛病：模型**发现了矛盾，但把先出现的那句当成错的**。
样本 c3 里前文写「门板上钉着七颗铜钉」、后文写「一共六颗」，模型报的是前一句，
建议「改为六颗铜钉」—— 作者照着改，就把对的那句改错了。颜色类的 holdout 样本同样复现。

### ⑤ 工具查多了会把整章审查搞崩（健壮性）

提示词强制查前文之后，c6 那次查了 10 次工具，模型最后回了一段自然语言
（`I have enough to report. Findings: ...`）而不是 JSON → 结构化输出解析失败 → **整章没审成**。
表现就是「这次审查没能完成，请稍后再试（本次不消耗免费字数）」。
这是「强制查」引入的新失败模式：不修的话，改善的是漏报、恶化的是可用性。

### ⑥ 同一处问题重复报（噪声）

c6 里「沈青悟」出现 3 次，模型报了 3 条。清单变成噪声（不是误报，但要占作者的注意力）。

## 改了什么

| 改动 | 解决 |
|---|---|
| `ChapterService.pageChapterMetaByNovel`（不做归属校验），工具改用它 | ① |
| 工具页大小改用 `PageParam.MAX_PAGE_SIZE`，并修掉末页判断 | ② |
| 提示词：人名/专有名词与数字**必须**用工具核对，并说明查不到就查前两个字 | ③ |
| 提示词：以**先出现**的写法为准、报后出现的那一处、建议里写明依据 | ④ |
| 提示词：工具最多查 3~5 次；工具报错时**如实写明「这一项没能核对」**；最后一条消息只回 JSON | ⑤ |
| 提示词：同一处问题只报一次 | ⑥ |

提示词单独成类 `ChapterReviewPrompt`，配了 4 条守门测试（工具名要对得上、四类名不能少、
六条撑指标的约束不能被静默删掉、不能漏实现细节）。

## 第二轮：把跨章一致性做成机制（作品级名词表）

`after2` 之后，跨章一致性靠的是「提示词要求模型必须用工具去查前文」—— **仍然是「模型愿不愿意照做」**。
所以又加了一层，不指望模型的自觉：

1. **攒表**：审查时模型顺带返回本章的专有名词（结构化输出的 `names` 字段），
   服务端校验「必须在本章正文里原样出现」之后写进 `t_novel_glossary`，记下**首次出现的章号**。
2. **注入**：审下一章时，把「本书已确立的写法（第 N 章）」放进提示词，模型照着对一遍。
3. **服务端比对**：本章出现「与表里某个名字同长度、同位置只差一个字」的写法，
   直接产出一条「前后不一致」，建议里写「前文第 N 章作 X」，与模型报的走同一套去重键合并。
   **这一步不看模型脸色。**

### 中间踩的坑（有数据）

第一版把 2 字名字也纳入比对，结果全文审查的报告数从 18 涨到 **38**、精确率掉到 **74%**：
表里有个「灯市」，一章写灯笼的正文里「灯下 / 灯还 / 灯芯 / 灯笼 / 灯纸」全被判成
「与第 4 章的『灯市』不一致」—— 10 条全是误报（明细见 `reports/glossary1.md`）。

收紧两处之后干净了：
- 服务端只扫 **3~4 字**的名字（3 个字只有在完全同位置上替换一个字才可能命中，
  而真实的名字错误 —— 沈青梧/沈青悟、萧战天/肖战天 —— 正好都在这个长度；2 字碰撞面太大）；
- 提示词要求**只列真专有名词**，不列普通器物（灯、刀、纸、铜钉这类）。

报告数回到 22，**精确率 100%**。

**它不依赖模型这一次想不想查** —— 这才是这一轮真正拿到的东西。

### 两个必须说清的副作用

1. **模型不再调工具了**（16/12 → 0/0）。表把「写法核对」接手之后，模型连情节衔接也不去读了。
   中途加了一条「表只解决写法对不对，错别字/语病/标点仍要逐句看」，章内召回从 17/20 回到 18~19/20，
   但工具调用没有回来。**数字类跨章矛盾（刀是两尺还是三尺）因此仍然完全靠模型**：dev 全文检出了、dev 单章与留出集都没检出。
2. **表里会混进错写**（模型把「灯心」「糖胡芦」当专名报了），这一轮就吃到一条真误报：
   表里存的是「灯心（第 3 章）」，模型拿它当标准，反过来把本章正确的「灯芯」报成错的。
   解法方向已经清楚（注入时把「只差一字的表内条目」归成一组、让作者定夺），本轮没做。

### 这条机制的边界（什么时候不能信它）

- **表空的时候没有基准**：第一次审某章时无从比对。全文审查是并发消费，
  所以第一次跑一本新书时，先被处理的章拿不到后处理章的名字，第二轮才稳定。
- **表里可能混进错写**：后果是同一个错写**只会被报一次**（第一处会报），后面再写就不报了 —— 少提醒，不是报错。
- **2 字名字**（「阿七」这类）只有提示词那一条路，服务端不判。

### 这一轮花的钱

评测 9 轮、约 90 次模型调用（`ai:platform:usage` 从 106 涨到 ~190），全部用 admin 账号跑，
**没有消耗任何用户的免费字数**。

## 第三轮：治表的污染、把数字变成机制、把工具调用找回来

上一轮留了三件「下一步」，这一轮按顺序做完了，每件都带数据。

### 一、治表的污染：只差一字的表内条目归成族

问题：表里存着模型报错的「灯心」，于是本章正确的「灯芯」被报成「应改为灯心」—— 方向反了。
根因不是比对逻辑，而是**我们不知道哪一边对**：表里的那条本身可能就是模型报上来的错写。

做法是承认这一点，改成按**手里有多少证据**分档给语气：

| 手里的证据 | 报告里怎么说 |
|---|---|
| 那个写法在**多个被审过的章**里都出现过（`hitCount >= 2`） | 「前文第 N 章作 X，此处应一致」 |
| 这一族里有两种写法（本书都用过） | 「本书两种写法并存，请统一为其中一种」 |
| 表里只有一条、且只出现过一次 | 「前文第 N 章作 X，本章作 Y，请确认统一为哪一种」 |

同时**修掉一个漏报**：以前两种写法都进了表之后，「表里已有这个写法」的跳过条件会把它们全挡掉 ——
书里明明有两种写法却永远不报。现在它们归到一族里，由族内比对兜住。
注入提示词时同族的写法也摆在一起（`灯芯（第3章）／灯心（第6章）`），并写明「两种都用过，不要断言哪种对」。

### 二、修「写对五处、写错一处会漏报」—— 顺带浮出一条新误报

那个跳过条件还造成另一个漏报：一章里「沈青梧」写对五次、「沈青悟」写错一次时，
只要本章出现过标准写法，整条比对就跳过，写错那处永远报不出来。去掉它之后，新问题立刻来了：
表里的「旧地图」开始跟正文里的「搁**在地图**边上」「**把地图**卷起来」撞上 ——
`family1` 那一轮多出两条误报（原句在 `reports/family1.md`）。

补的判据：**差异位置上不能是虚词**。真实的写法错误差异字都是实词
（青 / 清、芯 / 心、萧 / 肖），虚词（在 / 把 / 的 / 了）几乎不会出现在那个位置。
加完之后从 `fact1` 起这类误报归零。

### 三、设定数字：写法之外的第二张表

数字矛盾（刀是两尺还是三尺）以前完全靠模型读前文；而表上线后模型更不读前文了（工具调用 16/12 → 0/0）。

1. **攒表**（`t_novel_fact`）：模型顺带返回 `facts`，形如 `"伞骨=七根"`。
   服务端过三道校验才入库：名词在正文里、数值在正文里、**两者相距不超过 10 字** ——
   不校验距离的话，「他今年二十八岁，柳砚秋站在门外」会被读成「柳砚秋=二十八」。
2. **比对**：同一个东西本章写的数与表里不同就报一条，**中性表述**（「请确认以哪个为准」）——
   数值哪个对取决于作者的设定，我们手里只有「先写下的那个」。
3. **先归一化再比**：`NumberWords` 把「七根」与「7 根」都还原成 7。
   直接比字符串的话，「七根 → 7 根」就是一条误报。

### 四、把工具调用找回来

提示词里把两类核对**分开下指令**：写法照表对（不用再查前文）、
情节衔接与数字必须用工具读前文（给 3~5 次的预算）。
效果：工具调用从 0/0 回到 **11 次**，跨章核对重新有了「模型自己查」这一路。

### 五、评测自己查出来的一个真 bug：结构化输出加字段会让解析偶发失败

`fact2` 那轮 dev 的 c6 审查失败了（界面上是「这次审查没能完成，请稍后再试」）。日志里是：

```
JsonMappingException: Should never call `set()` on setterless property ('facts')
  through reference chain: ChapterReviewReport["facts"]
```

根因：模型返回的 JSON 会**把同一个字段写两遍**（`"facts":[...],"facts":[...]`）。
Jackson 是收集完所有属性才构造 record 的，所以**最后一个字段**遇到重复键时对象已经建好了，
它会去调 setter，而 record 没有 setter —— 直接抛异常，整章审查作废。

用探针逐个试过（`ChapterReviewReportTest` 把结论钉住了）：

| JSON 形态 | record 能不能解析 |
|---|---|
| 正常 / 字段缺省 / 为 null | ✅ |
| `names` 重复（中间字段） | ✅ |
| `summary`、`issues`、`issue.type` 重复 | ✅ |
| **最后一个字段重复** | ❌ `setterless property` |

也就是说**这个雷一直埋着** —— 在 `facts` 之前，最后一个字段一直是 `names`，只是没被踩到。
修法是把两个类型从 record 换成带 setter 的类（重复键退回成「以后一个为准」）。

**两条都是模型报的，不是机制判的**。

### 这一轮**没**拿到的（说清比好看重要）

- **dev 的「刀：三尺 / 两尺」仍然没检出**。数字机制本身成立了（留出集那处 2/2 检出，是服务端判的），
  但它的覆盖度取决于**模型有没有把那个数字报进表** —— 实测 8 章只攒到 2~3 条，
  dev 的「那把刀有三尺长」模型始终没报。`fact3` 的提示词已经改成「普通器物也行」并加了例子，
  但要更多样本才看得准。
- **单章跨章召回仍是 50%**：dev 那 2 处跨章问题里，人名那处稳定检出，数字那处时有时无。

## 第四轮：给跨章核对加向量检索（RAG）

前三轮把跨章一致性做成了「两张表 + 邻近检索（±10 章）」：表管**名字写法**和**模型报上来的数字**，
再往外 —— 「前文对某个东西的设定是什么」—— 只能靠模型自己想起来去调工具查。

这一轮把 RAG 的地基做出来，顺带**证明了一件比技术更重要的事**（见最后一节）。

### 地基（都是实测过的，不是照文档写的）

- embedding 用百炼 `text-embedding-v3`（**DeepSeek 没有 Embedding API**，2026-08 核实）。
  两条硬约束写进注释并加了启动校验：**单次最多 10 条**（传 25 条直接 400）、
  **维度写进 ES mapping 就改不了**。
- 章节正文切块（400 字/块、重叠 60 字、切点对齐句末）→ `dense_vector` 索引（1024 维、cosine）。
  写入顺序是「先写新块再删旧块」—— 反过来中间失败会让这一章从索引里彻底消失，而检索不到不报错。
- 回填：`POST /novel/vector-reindex?novelId=`（admin，限定一本）。实测 12 章 → 12 块、每章 150~500ms。
- **检索质量先量了再动手**：查询「这把伞的骨架是几根」（**不含「伞骨」二字**）→ 目标句 0.79、
  第二名 0.49、**区分度 0.31**。关键词检索在这种查询上查不到，所以这件事值得做。

### 试金石样本

`cases/far-cases.json`：第 1 章写「刀身三尺」，第 12 章写「那件兵器两尺出头」。
两章**相距 11 章**（超出邻近检索的 ±10 章），第 12 章又**没说「刀」**
（名词表按名字精确匹配，也兜不住）。—— 只有按语义翻全书才可能查到。

### 三轮尝试，前两轮都失败

| 做法 | 结果 |
|---|---|
| 模型自己调工具（提示词只写「必须查」） | **0 次工具调用**，自评写「仅给出单章片段，未提供可检索的前后文范围」 |
| 模型自己调工具（把「尺寸类必须查一次」写成硬要求） | 模型在总评里写「**已尝试用检索工具核对前文设定，但工具未能返回有效结果**」—— 而**日志里 0 次调用**。它自称查过，实际没查 |
| **服务端自动注入**（本轮最终做法） | **3 次全检出** |

第二行那个失败比第一行更坏：作者会以为「系统查过了、只是没查到」，而那条路根本没走过。

自动注入跑出来的原文（同一章连着跑三次，结果一致）：

> 前文第1章写的是「刀身三尺」，此处「两尺出头」与之矛盾，应改为与第 1 章一致的长度（如「三尺」）；
> 且第 1 章已称其为「刀」，此处「那件兵器」宜统一写作「那把刀」。

日志里对应的是：注入 3 条前文（来自第 1、9、7 章，共 102 字）。
注意后两条（第 9、7 章）与本章无关 —— 模型自己在总评里排除了：
「第 9、7 章的两条前文片段与本章无对应关系，不构成矛盾」。**注入几条、让模型判断，是可行的。**

### 结论：跨章核对里，「等模型自觉」的路径都不可靠

三轮下来这句话被验证了三次（提示词 → 工具 → 硬要求）。**能靠机制的就别靠提示词**：

| 要核对的东西 | 谁来做 |
|---|---|
| 名字写法 | 名词表（服务端比对，不看模型） |
| 模型报上来的数字 | 设定数字表（服务端比对） |
| 换说法的、相距很远的 | **服务端主动检索前文，直接摆进 prompt** |

一个必须说清的代价：自动注入之后，**模型不再需要调工具了**（本轮 0 次工具调用）。
「模型自己去找线索」这条路会越来越淡 —— 这不是坏事，但要清楚它的含义：
**检索没覆盖到的东西，模型也不会再主动去翻了。**

## 第五轮：块粒度（每块多少字）到底影响什么

前四轮里，检索用的块大小一直写死 **400 字**，代码注释里自己承认「没有调过参」。
之所以敢这么留着，是因为评测样本每章只有 150~260 字 —— **整章一块**，这个参数从来没被触发过。
而真实章节是 **3700 字**（《邪修天王》前 80 章，章长 2700~8000），400 字一块意味着每章约 10 块。

### 前提：实验里的切块必须与生产代码逐字一致

多粒度要跑 4 组，每组都改 Java 常量重新打包重启不划算，所以把 `ChapterChunker` 逐行复刻成
`eval/chunk_impl.py`。复刻这件事本身必须先被证明：

- 拿 4 个真实章（第 3/11/24/40 章，共 43 块）让 Java 探针 dump 结果，两边**逐块比 SHA-256**：全一致；
- 之后把「一致性」长期钉住：`eval/fixtures/chunker-golden.txt`（自编测试文本，不含任何作品内容）
  + `chunker-golden-hashes.txt`，Java 的 `ChapterChunkerGoldenTest` 与 Python 的
  `chunk_impl.py --golden-check` **两边都盯着同一份清单**。以后谁改了切块逻辑，
  两边都会红 —— 而不是让这一页数字悄悄失效。

### 两套样本

| | 章节 | 查询 | 用途 |
|---|---|---|---|
| 主集 | 前 40 章（13.5 万字） | 26 条 | 看趋势 |
| 留出集 | 第 41~80 章（15.4 万字） | 26 条（另一批事实点） | 验证结论稳不稳 |

查询都是「照着原文事实改写的提问」，分两类：**A 类**提问里带实体名（关键词检索本来也能命中），
**B 类**不含原句的专名与独特词（只能靠语义）。每组都**同时跑关键词检索（IK）做对照** ——
A/B 只是人工标注，结论以实测为准。

判定口径有两级，**第二级才是生产口径**（审查时是把 3 条摆进提示词的）：

- **Top1 有用**：第一名既命中正确章、那个块又真的覆盖了依据句；
- **Top3 里有一条有用**：三条里至少有一条能当依据。

### 结果

主集（前 40 章）：

| 粒度 | 块数 | 每章块数 | Top1 块长 | 向量·Top1 | 向量·Top3 | **Top3 有用** | Top1 有用 | 关键词·Top1 | 分差 |
|---|---|---|---|---|---|---|---|---|---|
| 200 字 | 788 | 19.7 | 176 字 | 16 | 22 | **19** | 14 | 9 | 0.019 |
| 400 字 | 405 | 10.1 | 371 字 | 16 | 23 | **20** | 13 | 9 | 0.014 |
| 600 字 | 275 | 6.9 | 578 字 | 19 | 22 | **19** | 13 | 10 | 0.016 |
| 1000 字 | 175 | 4.4 | 894 字 | 17 | 21 | **18** | 14 | 9 | 0.021 |

留出集（41~80 章）：

| 粒度 | 向量·Top1 | 向量·Top3 | **Top3 有用** | Top1 有用 | 关键词·Top1 | 分差 |
|---|---|---|---|---|---|---|
| 400 字 | 11 | 16 | **14** | 9 | 13 | 0.016 |
| 600 字 | 13 | 17 | **15** | 11 | 11 | 0.015 |

### 结论一：粒度不是关键变量 —— 所以不动

在最贴近生产的口径（Top3 里有一条有用）上，**200/400/600/1000 是 19/20/19/18**（主集）、
**14/15**（留出集）。差不超过 2 条、方向还不一致 —— 这是噪声。

600 在「Top1 命中」上两套都略高（19 vs 16、13 vs 11），但这个提升**经不起追查**：
主集里 600 多命中的那几条，「命中且覆盖依据句」的比例反而更低（400 是 14/16 = 88%，
600 是 14/20 = 70%）。也就是说**块变大带来的是「蒙对章」，不是「找准那一段」** ——
块越大，向量越接近「这一章在讲什么」的平均值，越容易匹配到正确的章，
但给出来的那一段未必是要找的东西。

**这一条值得单独记下来：只看 Top1 命中率会误选大块。** 判断检索质量必须问「给出来的那段对不对」，
而不是「章号对不对」。

所以块大小**保持 400 不变**。改它要全量重建索引（重新 embedding 所有书），
而两套数据都拿不出「改了确实更好」的证据。

### 结论二：RAG 的价值在「换说法」上被实锤

| | 主集 A 类 | 主集 B 类 | 留出集 A 类 | 留出集 B 类 |
|---|---|---|---|---|
| 向量检索 Top1 | 8/16 | **8/10** | 8/16 | **3/10** |
| 关键词检索 Top1 | 6/16 | 3/10 | 11/16 | 1/10 |

B 类（提问里不含原句的词）上，关键词检索基本失效（1~3/10），向量能到 3~8/10。
**这正是上一轮加向量检索的理由，现在有数字了。**

### 结论三（本轮最有用的发现）：该调的不是粒度，是「把两种检索合起来」

顺带算了一个组合口径：**关键词 Top3 的章 ∪ 向量 Top3 的章**里有没有正确章。

| | 向量 Top3 | 关键词 Top3 | **并起来** |
|---|---|---|---|
| 主集 · 400 字 | 23 | 15 | **24** |
| 主集 · 600 字 | 22 | 18 | **26（全覆盖）** |
| 留出集 · 400 字 | 16 | 17 | **21** |
| 留出集 · 600 字 | 17 | 16 | **22** |

留出集上从 16~17 抬到 **21~22**（+5 条）—— 比调粒度的收益大一个数量级。
逐条看也清楚：主集 400 字下「只有向量命中」的有 9 条、「只有关键词命中」的有 1 条；
留出集则是 4 条对 5 条 —— **两者各有各的盲区，互补性很强**。

现在生产只用了向量那一路。**下一步该做混合检索，而不是继续调块大小。**

### 两条附带结论

- **分差普遍只有 0.014~0.021**（Top1 与 Top2 的相似度差），与粒度无关。
  含义很实际：**任何「按分数阈值过滤」的策略都不可行** —— 分数高低区分不出「找对了」和「找错了」。
- **依据句被切散 0/26**：本批样本的依据句都在单句内，而切点落在句末，所以没测到
  「一句话被两个块各占一半」的情形。这是这一轮的**已知局限**，不是结论。

### 这一轮的局限（读数字时要一起读）

1. **只能同书内验证**：主集与留出集都出自《邪修天王》（现代网文，实体名多）。
   没换第二本书 —— 公版书（文言白话、硬换行多）的查询构造成本高，本轮没做；
2. **26 条 × 2 套**，样本小，绝对数字依赖样本，**只有相对对比有意义**；
3. 生产的检索是「多个查询各取 3 条再合并」，比实验里的单查询 Top3 更宽松，
   所以本文的数字是**保守下界**；
4. 实验用的 Python 切块实现与生产一致（有哈希证明与长期锚点），但**它本身不参与生产** ——
   结论落到产品上仍然是改一个常量的事。

## 第六轮：把检索做成混合的（向量 + 关键词）—— 以及一次「指标好看、端到端没用」的教训

第五轮的结论里写着「下一步该做混合检索」：向量按语义找、关键词按字面找，两边盲区互补。
这一轮把它做出来，然后在**真实审查链路**上量了一遍 —— 结果比预期复杂。

### 做了什么

1. **`HybridRanker`（RRF 融合）**：两路各取 `topK × 2` 候选，按 `1/(k + rank)` 求和，取前 topK。
   - **为什么用 RRF 而不是加权求和**：两路分数不同源 —— 一边是余弦（实测 Top1 与 Top2 只差
     0.008~0.021），另一边是 BM25（量纲随词频变，这次实测同一次查询是 10.685 与 9.857）。
     加权权重只能拍脑袋，而且换个数据集就失效。RRF 只用排名。
   - **`k` 取 10，不取文献默认的 60**：60 是给上千候选设计的，这里每路只有十几条，
     用 60 会把排名信息抹平（62/61 ≈ 1.016，几乎同分）。
2. **`text` 字段改成可检索 + IK 分词**（原先 `index = false`，那是为「只走向量」建的）。
3. **启动时校验 + 不一致就阻塞启动**（`ensureIndex`）：老索引上 `match` 查询**返回 0 条且不报错**，
   混合会悄悄退化成纯向量 —— 这是典型的「静默失效」，必须拦在启动阶段。
4. **诊断端点** `POST /novel/vector-search`（admin，支持 `mode=vector|keyword|hybrid`）：
   让评测直接打生产代码路径，而不是复刻一份检索逻辑。它同时解决了运维里最难查的一类故障 ——
   「前文检索不到」在界面上只表现为「这章没报跨章问题」，跟「确实没问题」一模一样。

### 一个绕不过去的前提：**索引必须删掉重建**

`analyzer` 与 `index` 和 `dense_vector` 的维度一样，**写进 mapping 就改不了**。
所以升级要按这个顺序：停服 → 删 `chapter_chunk` → 起服（自动按新 mapping 建）→ 回填
（`POST /novel/vector-reindex?novelId=`，一本一本）。本机实测：邪修天王 232 章 2585 块，141 秒。

### 检索层：混合确实更好，但没有宣传的那么多

生产接口实测，52 条查询（主集 26 + 留出集 26）：

| 走法 | Top1 里含依据 | Top3 里含依据 | Top5 里含依据 |
|---|---|---|---|
| 只向量 | 17/52 | 26/52 | 30/52 |
| 只关键词 | 11/52 | 19/52 | 23/52 |
| **混合（RRF）** | 16/52 | **28/52** | **31/52** |

另外一组（`fusion_probe.py`，候选给到 Top10）更能说明问题：
**「有用的那一条根本没被检索到」的次数 —— 只向量 18 次，混合 11 次**。

两组数字**必须一起看**：候选给足时混合能捞回 7 条，但取前 5 条时只多 1 条 ——
说明混合捞回来的东西大多排在后面。所以「混合提升了多少」这句话，
**不带上候选数就是错的**。

融合策略也是量出来的（`fusion_probe.py` 并排跑了 7 种，主集 + 留出集）：

| 策略 | Top1 有用 | Top3 有用 | Top5 有用 |
|---|---|---|---|
| 只向量 | 17 | 26 | 34 |
| RRF(k=10) | 16 | **28** | 40 |
| RRF(k=60) | 15 | 28 | 40 |
| 向量优先+补位 | 17 | 26 | 40 |
| 交替取 | 17 | 27 | 40 |

RRF 胜出：Top3 最好、Top5 并列最好，且**未命中数最少**。代价是 Top1 略差 ——
这跟第五轮那条「Top1 会误导」是同一件事：RRF 会把「两路都沾边」的条目提到前面，
挤掉「只有向量排第一」的那条。**报指标必须与实际注入条数对齐**（这里是 3~5 条，看 Top3/Top5）。

### 端到端：混合没有测出提升，而「多注入两条」反而有害

同一批样本（dev 6 章 20 处标注），在**同一个重建后的索引**上切配置：

| 配置 | 单章·章内召回 | 全文·章内召回 |
|---|---|---|
| 纯向量 + 3 条（上一轮的旧索引） | 19/20 | 19/20 |
| 纯向量 + 3 条（新索引） | 18/20 | 17/20 |
| 混合 + 3 条 | 17/20 | 19/20 |
| **混合 + 5 条** | **17/20** | **17/20** |

读出来的三件事：

1. **混合在端到端上没有可测量的差异**（单章 −1、全文 +2，都在 ±1~2 条的噪声里）。
   检索层的「未命中减半」没有变成「审查更准」。
2. **注入 5 条是有害的**：单章 19/20 → 17/20。多出来的两条多数与本章无关，
   把模型对本章正文的注意力拉走了。
3. 后面两行与第一行的差异里，有一部分只是**索引重建**带来的（同一配置从 19/20 变 18/20）。

**所以定稿配置是：混合开着、注入 3 条**（`app.rag.max-context-chunks` 默认 3）。
混合保留的理由不是「更准」，而是「更不容易一条都找不到」，且成本几乎为零
（多一次 ES match，约 +10ms）；一个配置开关就能回退。

### 这一轮最该记住的一条

**「检索指标更好」不等于「端到端更好」。** 注入 5 条在检索口径上多覆盖 13 条，
端到端却掉了 2 条 —— 因为多出来的片段在稀释模型对正文的注意力。
判据必须落在**最终产物**上（审查报告对不对），不能停在中间环节。

还有一条方法论的：**每加一个变量，上一次的对照就作废**。
这一轮第一次比较是「混合 + 5 条」对「上一轮纯向量 + 3 条」，中间隔着一次索引重建 ——
差异里混进了索引的影响，分不清是谁的功劳。重跑「同一索引、只切 hybrid 开关」才看准。

### 端到端的正确性验证（那个试金石样本还在）

`far-cases` 第 12 章（「那件兵器两尺出头」对第 1 章的「刀身三尺」，相距 11 章）：
混合检索下**单章与全文各检出 1 条**，原文：

> 发现一处前后不一致：兵器尺寸与第1章「刀身三尺」矛盾，本章作「两尺出头」。

另外第 1 章的总评自己写着「本章为第 1 章，没有更早的前文可供核对……这一数字项未能核对」——
**没有编造「已核对」**（这正是第四轮修掉的那个毛病）。

## 第七轮：补数字的覆盖度 —— 让服务端自己去正文里扫数字

第三轮把「跨章数字核对」做成了表（`t_novel_fact`），但留了个明摆着的缺口：
**表里的条目全靠模型在审查时报**（结构化输出的 `facts`）。模型不报，这一章既不比对、
表里也不新增。实测 8 章只攒到 2~3 条，dev 集那处「刀 三尺 / 两尺」漏掉的根因就在这 ——
第 1 章从没报过「刀 = 三尺」，第 6 章写「两尺」时无据可比。

这一轮把这条来路补上：**服务端拿名词去正文里扫它紧邻的数量短语**。

### 做法

1. **候选名词两个来源**：表里已有的名词（这样只要记过一次，后面每章都能比）
   加上本章模型报的专有名词（`names`）。
2. **扫的方向是两边**：「刀有三尺长」（名词在前）与「两尺长的刀」（名词在后）都认 ——
   dev 那处漏报的原文正好是后一种，只做前向扫描会白做。
3. **四条限制，方向是「宁可漏、不可误报」**（扫出来的每一条都会成为后面每一章的判据）：
   - 名词与数值之间不超过 4 字，**且中间不能有标点**（标点是「同一个短语里的数值」
     和「下一句碰巧出现的数值」之间最可靠的分界）；
   - 数值**必须带量词**，且量词限定在**尺寸/数量/年龄类**（根/尺/斤/岁/枚…）——
     把「天/年/月/日」这类时间词挡在外面，否则「沈青梧三天没合眼」会记成「沈青梧 = 三天」，
     然后后面每一章写「五天」都要报一次假矛盾；
   - 名词 1~4 字（**下限放到 1** 是故意的：数字核对的名词常常就是单字 —— 刀、伞、剑、门）；
   - 一个名词要**试遍它在正文里的每一处出现**，不能只看第一次。
4. **提示词加了一条**：`names` 除了专有名词，还要列**本章被量过的东西**
   （「那把刀有三尺长」里的「刀」、「伞骨一共九根」里的「伞骨」）——
   哪怕一两个字。原先这里写的是「不要列普通器物」，那条限制是为了压住写法表的误报，
   保留；只对「被量过的」开一道口子。
5. **数值形态严格化**：模型报的值必须是**纯数量短语**。原先只校验「能解析出数」，
   而 `NumberWords.parse("七颗铜钉")` 照样返回 7 —— 表里于是留过一行「门板 = 七颗铜钉」。
6. **加一列 `source`**（`model` / `scan`）：两条来路的可信度不一样，出问题要能分开看。

### 实测（dev 集 6 章，facts 表先清空、按 c1→c6 顺序跑）

清空前的表（全靠模型报，4 条，其中还有一条脏值）：

| 名词 | 值 | 来源 |
|---|---|---|
| 雨夜 | 三年前 | model |
| 铜钉 | 七颗 | model |
| **门板** | **七颗铜钉** | model（脏值：值里拖着名词） |
| 麻绳 | 一根 | model |

清空后重跑，**从零攒出 4 条**：

| 名词 | 值 | 来源 | 首次章 |
|---|---|---|---|
| **刀** | **三尺** | **scan** | 第 1 章 |
| 铜钉 | 七颗 | model | 第 3 章 |
| 旧邮票 | 一枚 | scan | 第 5 章 |
| 旧地图 | 一张 | scan | 第 6 章 |

**3/4 是服务端自己扫出来的**，而且「刀」这条正是原来漏掉的那个。

顺手看服务端自己比出的那条（日志原文）：

> 名词表：本章「刀=两尺」与前文第 1 章的「刀=三尺」不一致

### 效果与代价

- **原来漏报的检出**：c6 现在报出「那把两尺长的刀…前文第 1 章写「那把刀有三尺长」」——
  这条在第三轮、第五轮、第六轮都没出来过；
- **单章章内召回 16/20**（前几轮是 17~19/20）—— 在 ±1~2 条的噪声内，没有可见回退；
- **误报没有增加**：单章「未命中（误报候选）」仍是 1 条，而且那条是模型报的
  （「七颗铜钉 / 六颗」方向反，老问题），不是扫描带来的；
- 全文审查回归 17/20，任务正常完成。

### 局限（决定什么时候不能信它）

1. **扫描本身不认字，只认形态** —— 一个名词只要后面紧跟着数量短语就会被记下。
   靠四条限制压着，但不可能压干净：如果正文里有「刀一共三把，另有两把在鞘里」这种句子，
   记下的会是第一次出现的「三把」。**报出来的冲突仍然要作者自己判断**，这一点没变。
2. **候选名词还是要有来源**：表里已有的 + 本章 `names`。所以第一次出现仍然依赖模型
   把那个东西列进 `names`（提示词现在明确要求列「被量过的器物」）。
   **这不是「完全不靠模型」，是「只靠它出材料、判定权在服务端」** —— 与整条链路的思路一致。
3. **时间类量词一律不扫**（天/年/月/日）：这是刻意的取舍，代价是「三天的路程」这种
   设定核对不到。要覆盖它得先能分清「时间点」与「时间跨度」，那是另一个问题。
4. **量词白名单是硬编码的**：遇到表外的量词（比如「斗」「石」这类古代单位）会漏。
   加白名单的成本很低，但需要先看到真实语料里的实例，不预先堆。

## 没做到 / 剩余风险

- **异形词与成语靠模型词汇量，提示词管不了**：「灯心→灯芯」几轮都漏
  （「象往常→像往常」「按耐→按捺」都检出了）。想覆盖得上一份规范词表，那是另一件事。
- **数字机制的覆盖度取决于模型报不报**：服务端比得很准，但前提是表里有那条数字。
  dev 那处「刀 三尺 / 两尺」就是因为模型从没把它报进表而漏掉的。
- **代价是变慢**：单章 1.5s → 2.8s，全文 12s → 15s，多出来的主要是工具往返。
  要不要为了跨章一致性付这个时间，是个产品选择 —— 也可以只对「开启全书一致性」的作品付。
- **工具只看当前章 ±10 章**，跨全书的核对靠全文审查，而全文审查是**逐章独立审**，
  每章各查各的。上千章的书里，第 800 章的名字写法和第 3 章对不对得上，现在查不到。
- **留出集只有 2 章**，样本量小，只能当方向性证据。
- **改动仍然是打包的**：族归并 / 虚词过滤 / 设定数字三件事在同一轮里上，没做隔离组。
  每一步的证据是「哪一类报告变了」，而不是「只动了这一个变量」。
- **表的质量**：模型仍会把普通器物、甚至它自己写错的名字报进来。后者在后续章节造成的
  反方向误报已由「族 + 分档语气」压掉；前者靠提示词约束，没有代码兜底。

## 下一步建议

1. **时间类设定核对不到**：量词白名单刻意排除了「天/年/月/日」——
   因为分不清「时间点」与「时间跨度」时误报太多。要覆盖它得先解决「这句话说的是一个时点、
   还是一段时长」，那是个更大的问题（可能得让模型标注，而不是靠形态）。
2. **把「元数据」也纳入交叉核对**：现在核写法与数字，其实章节顺序、人物年龄随时间的变化也能核。
3. **留出集扩到 10 章以上**，再谈百分比。
4. **补一组「只修 bug、不改提示词」的隔离组**，把这几轮真 bug 的收益和提示词的收益分开。
5. **把评测跑起来更省力**：现在每轮要手工打包重启实例、还得盯着免费额度
   （这一轮就被「今天的免费字数用完了」打断过一次，得重置评测账号的当日计数器）。
   改提示词时若能一条命令跑完（含 dev + 留出集），「改文案导致指标回退」就不会靠记性来防。
6. **给「注入条数」补一轮噪声带**：第六轮的结论（3 比 5 好）是单轮结果 —— 差 2 条，
   而同一份代码跑两次本来就会差 1~2 条。要坐实它，得同一配置跑两轮。

# 第八轮：先换一把更大的尺子（留出集 2 章 → 12 章）

这一轮**没有改提示词、也没有改机制**。改的是尺子 —— 因为前七轮所有百分比都建立在一个
2 章的留出集上，那个规模只能算「方向性证据」，不足以下结论。

## 做了什么

1. 留出集从 2 章扩到 **12 章 / 33 处章内标注 / 5 处跨章标注**（h2、h6、h12 三章章内干净，
   做误报基准）。结构与 dev 同构、换皮：人名「柳砚秋」、道具换成伞、标点错以半角问号与
   省略号误写为主、不一致换成颜色与数字，另加两类 dev 里没有的（时间点、姓氏）。
2. **每处缺陷都查了依据**，不凭手感 —— 标点依据 GB/T 15834-2011（4.11 省略号六连点、
   5.1.3 引号书名号成对、4.5 顿号用于并列词语、附录 A.2 问号以疑问语气为据）；
   异形词依据《第一批异形词整理表》GF 1001-2001 的推荐词形；语病只取教科书硬伤。
   拿不准的（例如书名号能否套用）**没有写进样本**。
3. 顺手把外层流程包成一条命令（`eval/run_all.py`）：起依赖、按需重编、起实例、
   增量补样本、跑样本集、出汇总，并把「额度不够就拒绝跑」和「本轮是否完整」接进报告。

## 扩容立刻逼出一个打分口径的真缺陷

跨章标注在旧口径里只认「标注挂在的那一章」。12 章一跑就露了：同一处人名写法矛盾
（h2 里写错、h4/h8/h10/h11 里写对）被报了 5 次，其中 4 次全被算成**误报**。
两个数同时错，而且错的方向会让人以为「模型爱瞎报」。

改成：跨章标注**整本只认一次**（其余算「重复报告」），判据是正文片段**或建议文本**里
出现该条目的特征串。**刻意不加 `type == kind` 门** —— 实测有一次模型把人名矛盾标成了
「错别字」，加类型门就会把这次真检出判成误报。

（改动只用 `rescore` 重算，没有多花一次模型调用。）

## 基线（单章审查，12 章留出集）

| 指标 | 值 |
| --- | --- |
| 章内召回 | 25/33 = **76%** |
| 跨章召回 | 4/5 |
| 报出 | 38 条，其中误报 2、重复报告 6 → **有依据的 95%** |
| 干净章 h6 / h12 | 各报 **0 条** → 误报基准成立 |

漏报的 8 处：4 处错别字/异形词（记念、就坐、涵蓄、雕谢 之类）、3 处语病、1 处标点
（引号只写前一半）、1 处章内数字矛盾。**漏报集中在「异形词」与「语病」两类** ——
这和 dev 集上的观察一致（异形词靠模型词汇量，提示词管不了）。

剩下两条没命中/误报的样例值得单独记：

- h11 把「十二文」拿去和第三章的「六只罐子」比 —— 一次**错误的跨章联想**（数字表象相同，
  其实指两样东西）。这类误报不是「模型瞎报」，是「它比了不该比的东西」。
- h2 让作者把 h2 里没写的布巾颜色补上 —— 模型拿第一章的章内矛盾来要求第二章。

这两条都留在了报告里，没删。

# 第九轮：先量噪声带（同配置跑 2 轮）+ RAG 隔离组（关掉注入跑 2 轮）

第八轮换了尺子，这一轮先量**尺子本身的抖动**。不做这一步，后面任何「改完涨了 5 个百分点」
都可能是运气。

四轮都在同一个 fixture 上跑（12 章留出集，向量索引已回填到 12/12 章），单章审查，
每轮开跑前评测账号当日用量都是 0，四轮的 `complete` 都是 true。

## 读数

| 轮次 | 配置 | 章内召回 | 跨章 | 报出 | 误报 | 重复 | 有依据 |
|---|---|---|---|---|---|---|---|
| noise-a | 默认（RAG 注入 3 条） | 27/33 = 82% | 3/5 | 38 | 3 | 4 | 92% |
| noise-b | 同上 | 29/33 = **88%** | 3/5 | 40 | 3 | 4 | 92% |
| norag | `app.rag.max-context-chunks=0` | 29/33 = **88%** | 3/5 | 36 | 0 | 3 | 100% |
| norag-b | 同上 | 25/33 = **76%** | 3/5 | 37 | 4 | 5 | 89% |

## 结论一：噪声带比我原先估的大得多

- **同配置两轮（noise-a / noise-b）章内召回差 6 个百分点**（82% vs 88%）；
  把两个配置的四轮放在一起看，范围是 **76% ~ 88%，12 个百分点**。
- 换算成「处」更容易记：**33 处里差 2~4 处**。1 处就是 3 个百分点。
- ⚠️ **这意味着前几轮里那些「+5 个百分点」的结论，按现在的尺子都落在噪声里。**
  那些结论没有被推翻，但**当时的说法偏强了** —— 它们更像是「方向性证据」，
  这一点要写进论文式的表达里，不能直接说「提升了 5%」。

### 为什么抖：波动集中在「前后不一致」一类

| 轮次 | 错别字 | 语病 | 标点 | 前后不一致 |
|---|---|---|---|---|
| noise-a | 9 | 5 | 10 | 4 |
| noise-b | 9 | 6 | 9 | 6 |
| norag | 9 | 6 | 10 | 5 |
| norag-b | 9 | 5 | 9 | **2** |

（数字是「命中报告数」，同一处被报两次会算两条。）

- **错别字 9/9/9/9 完全稳定、标点 10/9/10/9、语病 5/6/6/5 基本稳定（±1）。**
- **抖动全在「前后不一致」**（章内数字/颜色矛盾这一类）：2~6。
  一小类抖一下，在 33 处的小分母上就是 6~12 个百分点。
- 另有两个稳定信号可以当「没退化」的判据：**跨章四轮全是 3/5**、
  **两章干净章（h6/h12）四轮都报 0 条**。

## 结论二：在这个尺子上，RAG 注入的贡献量不出来

- RAG 开着两轮：章内 82% / 88%，误报 3 / 3。
- RAG 关掉两轮：章内 88% / 76%，误报 0 / 4。
- **两组完全交叉重叠** —— 差异（无论正负）都落在上一条那个噪声带里。

所以：**既不能说 RAG 有用，也不能说它没用**。而且这大概率不是「RAG 无效」，
是**尺子量不到它**：

- 12 章的跨章标注全都在「邻近检索 ±10 章」的射程内，名词表 + 邻近检索就能覆盖，
  RAG 在这里是冗余的。
- RAG 真正的场景是 `far-cases` 那种：**相距 11 章、且换了称呼**（「那件兵器」而不是「刀」），
  名字精确匹配和邻近检索都够不着。第七轮就是用它验的。

要拿 RAG 的账，得把 `far-cases` 扩到几十条再跑 —— 那是另一件事，记在下面。

## 结论三：跨章机制只覆盖三类不一致

四轮里跨章命中的**始终是同样 3 条**：伞骨数字、人名写法、布巾颜色。
稳定漏掉的是这 2 条：

| 漏掉的 | 为什么漏 |
| --- | --- |
| h5「他是晌午到的镇上」vs h1「天已经黑透了」—— **时间点** | 设定数字表只认数字；「晌午 / 天黑」不是数字，也不是名字 |
| h10「那位女子姓舒」vs h4「苏姑娘」—— **姓氏** | 名字表按「同长度差一字」归族，但「姓舒」不是名字形态，进不了表 |

**这两类恰好是 dev 集里没有、第八轮才加进来的。** 换句话说：模型/机制在
「名字写法、数字、颜色」这三类上是可靠的，**一旦换成时间点和称谓，就没人管了** ——
和之前「时间类量词刻意不扫」的取舍对上了，现在有了量化证据。

这一条直接影响下一步选什么：如果要继续补跨章能力，**优先级应该是「时间/称谓」**，
而不是再调 RAG。

## 这一轮改了/加了什么

- `run_all.py` 加 `--app-arg`（透传 Spring 参数），隔离组就是靠它做的：
  `--app-arg=--app.rag.max-context-chunks=0`。顺带确认这个开关语义干净 ——
  注入循环第一句就是 `picked.size() >= maxContextChunks`，0 直接不进注入。
- 发现并修了一个 fixture 问题：**10 个新补的章在索引里，但 h1/h2 不在** ——
  它们是 P1 修好之前建的，没有写入路径。用 admin 的 `/novel/vector-reindex` 回填到 12/12。
  这正是 P1 那个缺口的真实后果：老数据不会被自动补上，得手动重建一次。

## 下一步（按证据排序）

1. **要报结论，就得跑 N 轮取中位数/范围**，别再拿单轮差值说话。稳定子指标
   （错别字/标点/语病召回、跨章命中、干净章误报数）可以先看，它们抖得小。
2. **跨章补「时间 / 称谓」**（比调 RAG 优先级高，上面有证据）。
3. 真要量 RAG：把 `far-cases` 扩到几十条（远距离 + 换称呼），那是唯一能把它量出来的样本形态。

# 第十轮：跨章「时间点 / 称谓」——没做到，过程中还抓出一个假提升

第九轮把跨章漏掉的两条定死了：h5 的**时间点**（本章「晌午到的」vs 前文「天已经黑透了」）、
h10 的**称谓**（本章「姓舒」vs 前文「苏姑娘」）。这一轮专门去补它们。

## 结论先放前面：补不上

| 条件 | 跨章命中 | 章内召回 | 干净章（h6/h12） |
|---|---|---|---|
| 改前 · 注入 3 条 · 关注入 | 3/5 × 四轮（四轮恒定） | 76~88% | **0 / 0（四轮）** |
| 改后 · 注入 3 条 | **3/5 × 两轮** | 79%、91% | 0/1、0/0 |
| 改后 · 注入 8 条 | 3/5、4/5 | 79%、82% | **1、4（基准破了）** |
| 改后 · 但提示词里抄了样本原句 | 4/5 × 两轮（**假的**） | 79%、91% | 0/0 |

**「时间点」和「称谓」这两类，在当前模型 + 当前三层机制下报不出来。** 六轮改前基线恒定 3/5，
改后两轮还是 3/5。下面三步每一步都在排除一种解释。

## 第一步：先分清是「检索没找到」还是「模型拿到没比」

不验证就改等于瞎写，所以先用真实链路量了两条各自的形态：

| 漏报 | 检索侧 | 模型侧 |
| --- | --- | --- |
| h5 时间点 | **命中了**：注入了第 1 章那块 245 字，原句就在里面 | **拿到没报** |
| h10 称谓 | 默认 top-3 = 第 8/3/9 章，没有第 4 章 | —— |

两条的瓶颈不一样 —— 一条是模型侧，一条先看着像检索侧。

## 第二步：改提示词，把这两类写进「该去查什么」的动作清单

原来第四类的动作清单里只有「前文发生过的事」和「数量/尺寸/时长/年龄」；
「称呼突然变化」只写在四类的括号里，**没进清单**。模型执行的是清单，所以它不去比。

改动三处：① 四类描述补「同一件事发生的时间前后矛盾」；② 清单加两条（时间点、换个说法指称人物）；
③【相关前文】那段从笼统的「逐条对照」改成**五个维度各过一遍**。

**结果：跨章还是 3/5。** 两轮都是。动作清单没能让它去比。

## 第三步：把前文给到位（注入 3 条 → 8 条）

第二步没效果，怀疑是「该比的那一章根本没在提示里」（h10 的 top-3 里没有第 4 章）。
把 `app.rag.max-context-chunks` 放大到 10 再跑两轮 —— 第 4 章确实注进去了（8 条，1300 字）。

**结果：跨章 3/5、4/5，但干净章开始报东西（1 条、4 条）。**

⇒ 注入更多前文**没换来召回，先把噪声放进来了** —— 这正好解释了第九轮那条
「在 12 章射程内量不出 RAG 的账」：前文给得越多，模型越容易找到「可以报的东西」，
其中不少是误报。干净章是专门用来测误报的，它从 0 变成 1/4，说明这条路是负收益。

## 过程中抓到的假提升：提示词把答案喂给了模型

第二步改完第一次跑，跨章从 3/5 变成 **4/5**，两轮都是 —— 看着像个漂亮的提升。

**它是假的。** 我举例子时图省事，直接抄了留出集那两条标注的原文
（一个人物姓氏、一处时间词）当成提示词里的例子。于是模型在**别的章**的审查里
就开始念叨那个写法 —— 因为它刚从提示词里看到。

把例子换成虚构的（「姓赵」对「周掌柜」、「天没亮就出了城」对「日头偏西才出的城」），
顺手 `grep` 又清掉两处更早的旧例子（数量那一段也抄了留出集的道具与数字），
**跨章立刻掉回 3/5**。

留出集只用来打分。它的原句出现在提示词里，这个数就不算数了。

## 顺带量到的两件事

**① RRF 把关键词路的强命中挤掉了。** 用 ES 复现关键词那一路：h10 整段作 query，
**第 4 章排第 2**（BM25 69），稳在候选 10 条之内；融合后（`RRF_K=10`）掉到**第 8**。
原因是 RRF 只看排名不看分数：「一路很强」（关键词第 2 → 1/12=0.083）敌不过
「两路都还行」（任一块两路各进前十就是 1/20+1/20=0.1）。这是 RRF 的固有性质。
**但它不是这次的瓶颈** —— 第三步证明把第 4 章注进去也报不出来。

**② 检索结果本身有抖动。** 同一章同一个 query，两次 top-3 分别是（8、3、1）与（8、3、9）——
ES 的 HNSW 是近似搜索。所以「注入前文」这个机制自带随机性。

## 打分口径又修了一次（这次修的是跨章命中）

跨章命中的匹配原来用「正文片段**或**建议文本里出现特征串」。12 章样本下撞出两种认错：

- 一条讲**布巾颜色**的建议，因为引用的原句里含「九根伞骨」，被算成了**数字**那条的命中；
- 一条报**语病**（「回来缺少前提」）的建议，只在说明里顺带写了「前文提过晌午」，
  被算成了**时间矛盾**命中。

两种都让召回虚高。改成两层判定：**先看建议在讲哪一条**（要出现「不一致／矛盾／统一」
这类词，说明它确实在主张矛盾），看不出来才退回按正文片段的位置匹配。
九轮的全部报告已用 `rescore` 按新口径重算（没多花一次调用）。

## 服务端为什么没做自动比对

论证过，两条都做不出可靠判据，所以**没有硬写**：

- **时间**：样本里前文那句是「天已经黑透了」—— 这是**描述性表达**，不是「晌午/夜里」
  这种时段词。词表永远覆盖不全，而把样本里出现的词写进表，就是**为样本过拟合**。
- **称谓**：判断「姓舒」和「苏姑娘」是不是同一个人靠语义。收紧到「姓 X」模式再跟
  专名首字比，正文里泛指的一句「姓王的」就会误报一片。

## 改动留不留

提示词那三处改动**保留**了，理由是：跨章没降、章内召回在噪声带内（改前 76~88%、改后 79~91%）、
误报反而更低（均值 2.5 → 1.5）、干净章没变差。它的代价是**重复报告变多**（均值 4 → 7），
但重复报告是「同一处跨章矛盾在多个章里各报一次」，单章审查本来就是一章一看。
如果你想回到最干净的基线，这是一个自包含的改动，`git revert` 一个文件即可。

## 结论

「跨章时间/称谓」这一项**没能补上**，但它换来三件更值钱的东西：
① 一个**有证据的边界**（不是「模型可能不行」，是四轮 + 两轮 + 两轮量出来的）；
② 一条**评分纪律**（提示词里出现留出集原文，会让假提升看起来像真提升）；
③ 一个**下一轮该试的方向**（见下）。

下一轮如果还要碰这一类，唯一还有依据的走法是**服务端把「该比的两句」配好对**：
扫出本章的疑似时间句/疑似指称句，按句去检索前文，把「这一句与前文第 N 章那句可能说的是
同一件事」并排摆进提示词。它不替模型下判断（判据做不出来），只把「该比什么」从模型手里拿走 ——
而第三步已经证明，模型在「该比什么」上是不可靠的。这条没做，是因为没有证据表明它必然有效。

# 第十一轮：把 RAG 的账量出来了 —— 并且发现「融合在取前 3 条时会丢依据」

第九轮留下的话是「要量 RAG 的账，得把 far-cases 扩到几十条」。这一轮做了两件事：
把那份样本做出来，以及**给检索单独做一层评测** —— 结果第二件事先出了结论。

## 一、造一份「三套机制都够不着」的样本（`cases/far-cases-v2.json`）

24 章 / 9 处跨章对照 / 章内一律无缺陷。每一处都刻意做成：

| 绕开谁 | 怎么绕 |
| --- | --- |
| 邻近检索（只管当前章 ±10 章） | 对照的两章**距离一律 12 章**（f1↔f13 …… f12↔f24） |
| 名词表（按名字精确匹配） | 后面那一律**换称呼**：刀→那件兵器、石榴→那株树、黑麻绳→红绸、城南→城北 |
| 设定数字表（名词=数值） | 矛盾点不用「名词紧邻数值」这个形态，也不是专名写错一字 |

⇒ 这类矛盾要被检出，**只能是语义检索把前文找出来、再摆给模型**。

另外放了 **3 处「换了说法但事实一致」**（f21 酒肆旗子、f23 走了七天、f24 纸灰的颜色）——
它们是误报陷阱：把「换了个说法」当成「前后矛盾」报出来就记成误报。

**端到端两轮：跨章 8/9**（两轮都稳定漏 f19 —— 原因见第二节）。
这是 RAG 值钱的第一份硬证据：这些矛盾在射程外、还换了称呼，模型能报出来，
只可能是检索把前文送到了它面前。

## 二、给检索单独做一层评测（新工具 `eval/retrieval_eval.py`）

`review_eval` 报的「跨章命中」是**三段相乘**：检索找到 → 摆进提示词 → 模型去比。
哪一段掉了，从总数上看不出来 —— 两个方向都撞到过（注入进去模型也不报；两路都找到了、
融合却把依据挤出去）。所以新工具**只看第一段**：对每条跨章标注，看检索回来的**前文**块里
有没有哪一块含「前文那一半」的依据串 —— 也就是「模型要核对时，手里到底有没有那份依据」。

| 样本集 | 条数 | 向量路 | 关键词路 | 融合（取前 3） | 融合（取前 5） |
| --- | --- | --- | --- | --- | --- |
| review-cases（dev） | 2 | 2/2 | 2/2 | 2/2 | 2/2 |
| holdout（12 章） | 5 | 5/5 | 5/5 | **4/5** | 5/5 |
| far-cases-v2（24 章） | 9 | 9/9 | 9/9 | **8/9** | 9/9 |
| **合计** | **16** | **16/16** | **16/16** | **14/16** | **16/16** |

**两路各自都是满分，融合却各丢一条** —— 而且是「两路都找到了、融合之后没了」。
丢的那两条（h10 称谓、f19 左肩/右肩）正好是端到端里漏掉的那两条。

⇒ **不是融合算法错，是最终只取 3 条取少了。** 依据块排在两路的第 4~5 名，
融合后被「两路都排中游」的块压下去；取 5 条就回来了。

这条也把第十轮的遗留说清楚了：h10 当时是绕路量的（把注入放大到 10 条、看注入章号），
结论「检索侧丢了」；现在用通用工具直接复现，而且看清了**两路都找到了** —— 不是某一路差。

## 三、端到端验证：3 → 5 到底值不值

12 章留出集，两档各四轮（同一 fixture，注入条数是唯一变量）：

| 配置 | 章内召回（四轮） | 跨章 | 误报 | 干净章（h6/h12） |
| --- | --- | --- | --- | --- |
| 注入 3 条 | 82 / 88 / 91 / 79 %（均值 **85.0**） | **3/5 × 四轮**（连前两轮共六轮都是 3/5） | 3 / 3 / 2 / 1 | 0/0、0/1、0/1、0/0 |
| 注入 5 条 | 70 / 82 / 79 / 88 %（均值 **79.8**） | **4/5、4/5**、3/5、3/5 | 4 / 1 / 3 / 1 | 0/0、0/0、**1/1**、**1/0** |
| （注入 8 条，第十轮） | 79 / 82 %（均值 80.3） | 3/5、4/5 | 7 / 3 | **1/4、1/0（破了）** |

**三件事：**

1. **跨章有正向**：取 3 条时六轮恒定 3/5；取 5 条四轮里两轮到 4/5。
   多出来的那条是**「称谓」类** —— 取 3 条时它一次都没报出来过。
   这也修正了第十轮那句偏强的结论：不是「模型拿到依据也不报」，是**「很少报」**（概率低但非零）。
2. **章内那 5 个百分点的下滑按噪声处理**：均值 85.0 → 79.8 看着像降了，但它**不单调** ——
   注入 8 条那两轮均值 80.3%，并不比 5 条差。若「注入越多、章内越差」成立，8 条该更差。
   误报均值两档完全相同（2.25）。
3. **别再往上调**：注入 8~10 条时，两章专门用来测误报的干净章**破了**（报 1 条、4 条），
   而 3 条与 5 条时它们基本是 0。5 是「够用且安全」的那个点，不是越大越好。

## 四、顺手纠正一条写在代码注释里的错误结论

`ChapterReviewServiceImpl` 上原先写着：「3 是量出来的，5 试过、退回来了」，
依据是「注入 3 条时章内召回 19/20，注入 5 条掉到 17/20」。

**那条结论是读表读错的。** 去看它引的原始表格（第六轮）：

| 配置 | 单章·章内召回 |
| --- | --- |
| 纯向量 + 3 条（上一轮的旧索引） | 19/20 |
| 纯向量 + 3 条（新索引） | 18/20 |
| 混合 + 3 条 | 17/20 |
| **混合 + 5 条** | **17/20** |

「混合 + 3 条」与「混合 + 5 条」**都是 17/20** —— 根本没有差异。被拿来对比的是
「纯向量 + 3 条（旧索引）」和「混合 + 5 条」，中间多了**索引重建**和**混合开关**两个变量；
同表里同配置换一次索引就从 19/20 变 18/20，那张表本身的分辨率只有 ±1~2 处。

所以这不是「被新数据推翻」，是**当时就归因错了**。注释已改写，把这段过程留在里面。

（它与第十轮那条「提示词抄留出集」是同一类错：**结论跑在了数据的表达能力前面**。）
